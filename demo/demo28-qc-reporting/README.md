# demo28 — 預測性品管與階層報告鏈

> 模組 #28 ｜ Level 3 企業級 · 營運部門 · Manufacturing ｜ 部署 1 週 ｜ `ERP` `MES` `IoT`
> 來源：第 07 章 ch07_p11、附錄 G apxG_p16

Agent 輪詢 MES（**Plex / SAP**）取得各產線各班別的量測值與不良數，套用
**SPC 控制圖（UCL / Mean / LCL）+ Nelson Rules**，在**產生瑕疵的 3–5 個班次前**
發出趨勢警告，再把同一份底層資料整理成四階報告鏈送給四種完全不同的讀者。

## 本模組的技術重點：四階報告鏈（apxG_p16）

```
Shift End  →  Daily 06:00  →  Weekly  →  Monthly Board PDF Pack
現場領班        營運總監/廠長      品質經理      董事會
```

**同一份底層資料，四種呈現。** 四階不是同一份報告換個標題轉寄，而是**受眾、
聚合層級、詳細度、要回答的決策都不同**的四份文件：

| 階 | 受眾 | 聚合層級 | 詳細度 | 格式 | 這份報告要回答的決策 |
| --- | --- | --- | --- | --- | --- |
| **Shift End** | 現場領班 Supervisor | 單班 × 單線 | 逐點量測值、逐條 Nelson 判定、立即處置 | HTML / Slack | 現在要不要停線、調機、隔離本班產出 |
| **Daily 06:00** | 營運總監 / 廠長 Ops Director | 單日 × 全產線 | 跨班對比、當日趨勢、預測性警告 | PDF | 今天人力與稽核資源要壓在哪一條線 |
| **Weekly** | 品質經理 Quality Manager | 單週 × 全廠 | 週對週比較、產線排名、重複性問題 | PDF | 偶發還是體質問題，要不要開矯正措施單 |
| **Monthly** | 董事會 Board | 單月 × 全廠 | 高層摘要、月對月、風險登錄、決策建議 | PDF Pack | 要不要批預算換模具／擴編品保 |

**為什麼四階要分開寫，而不是一份轉發四次**

領班站在機台旁邊看手機，平均只讀 20 秒，他要的是「現在動不動手」。
董事會讀的是資源與承諾，他不知道 UCL 是什麼，也不該知道。
把班末報告轉給董事會，他讀不完；把董事會摘要轉給領班，他不知道要做什麼。
**受眾錯配比報告晚送更傷信任**——所以 `chain.TIER_PROFILES` 的受眾與格式
刻意不可由 `config.yaml` 覆寫。

四份提示詞（`prompts/*.md`）也各自獨立，且各自帶著自己的禁令。例如班末那份
禁止「把超規值講成接近規格邊緣」，董事會那份禁止「只報平均值」。

## 最重要的設計：品質異常絕不可被平滑掉

這是本模組唯一不可妥協的規則，也是整份程式碼的骨架。

### 問題長什麼樣子

mock 資料裡就藏著這個陷阱：`L1 射出成型 A 線` 在 2026-08-21 夜班有一點量測值
`12.5315`，超出 UCL `12.524`（Nelson Rule 1，重大警報）。但那一天：

- 該班不良率 **0.60%**，上限是 1.50% —— 沒超標
- 全線當日平均不良率 **約 0.45%** —— 更漂亮
- 全廠當日平均不良率 **低於 1.50%** —— 完全正常

**如果讓聚合邏輯決定警報要不要往上送，這則 3σ 超限會在第 2 階就消失。**
董事會月報只會看到「本月不良率 0.6x%，優於上月」，而超規那批貨已經出廠了。

### 三道機制

**1. 警報只做聯集，永遠不做平均。**
`chain._escalate()` 是**唯一**的往上傳遞路徑，它只做三件事：聯集、去重、排序。
這個函式刻意沒有任何 `filter` / `threshold` / `min_severity` 參數——只要簽名上
能加一個「只往上傳 critical」的旗標，早晚就會有人為了讓月報好看而打開它。

**2. 每一階之間有硬性完整性檢查。**
`chain.assert_no_alert_dropped()` 在班末→日、日→週、週→月三個交界逐一比對
警報 id 集合。下階有、上階沒有 → 拋 `AlertSuppressionError`，**整條報告鏈失敗，
exit code 2**。寧可整條鏈當掉，也不要送出一份會說謊的月報。

這比照 demo05「星等硬性決定路由」的精神：安全關鍵訊號不交給聚合邏輯決定。
品管場景的風險更直接——被平滑掉的那條 3σ 超限，下游就是客戶手上的瑕疵品。

**3. 平均值看起來正常時，強制印警示橫幅。**
高階讀者最容易犯的錯，是看到「全廠不良率 0.62%，遠低於上限」就翻頁。
只要仍有未結案警報，日／週／月三階的報告最上方一律強制加上：

```
> ⚠️ 2 件重大 / 3 件主要 / 5 件次要品質警報未結案。
> 本期彙總不良率 0.62%，即使落在容忍區間內，也不代表上列警報已解除。
> 品質異常不因平均而消失：任何一階偵測到的超標，四階都看得見。
```

**平均值決定敘述怎麼寫，永遠不決定警報要不要出現。**

### 連帶的三條小規則

| 情境 | 錯誤做法 | 本模組的做法 |
| --- | --- | --- |
| 某產線整期無資料 | 跳過該線 → 全廠平均**變好看** | 產生 CRITICAL `data_outage` 警報貫穿四階，並在彙總表獨立列出「未涵蓋產線」 |
| 某班投入數為 0 | 記為「不良率 0%」 | 不良率回 `None`、顯示「—」，並發 `no_output` 警報要人回答為什麼停線 |
| 上次的警報這次資料裡沒有了 | 報告上自己痊癒 | 從 state file 沿用（carry forward），標「沿用」直到人工結案 |

## SPC 與 Nelson Rules

### 控制界限來自基準線，不從當期資料反算

`mock/lines.json` 的 `baseline_mean` / `baseline_sigma` 是製程穩定期建立的基準。
若改用當期資料算 UCL/LCL，製程整體漂移時界限會跟著漂，於是**永遠「都在管制內」**——
這是 SPC 最典型的自欺，也正是 ch07_p11 要消滅的「隔天早上才發現」。

### 兩個判定層次

| 層次 | 點是什麼 | 抓什麼 | 對應書中 |
| --- | --- | --- | --- |
| **班內即時** | 該班的每一個量測讀值 | 單班內的失控（如單點超 3σ） | 「同一班別內即時偵測」 |
| **跨班趨勢** | 每一班的量測平均值 | 單班都還好、但一路往同一方向走 | 「在產生瑕疵的 3–5 個班次前」 |

兩層都套完整的 **Nelson Rules 八條**（`config.yaml` 的 `spc.enabled_rules` 可裁減）：

| 規則 | 判定 | 預設嚴重度 |
| --- | --- | --- |
| R1 | 單點超出 3σ 管制界限 | 🔴 critical |
| R2 | 連續 9 點落在中心線同一側 | 🟠 major |
| R3 | 連續 6 點持續上升或持續下降 | 🟠 major |
| R4 | 連續 14 點上下交替震盪 | 🟡 minor |
| R5 | 連續 3 點中有 2 點超出同側 2σ | 🟠 major |
| R6 | 連續 5 點中有 4 點超出同側 1σ | 🟠 major |
| R7 | 連續 15 點全部落在 ±1σ 內（變異被過度壓縮） | 🟡 minor |
| R8 | 連續 8 點全部落在 ±1σ 外（疑似混料） | 🟡 minor |

> **安全注意（apxG_p16）**：Nelson Rules 為異常判定依據，**不可用單點超限取代趨勢判定**。
> 因此 R2/R3/R5/R6 這些趨勢型規則預設全開，且與 R1 同樣往上浮。

**規格界限（USL / LSL）與控制界限是兩回事**：超出控制界限是統計異常（製程失控），
超出規格界限是**出貨風險**（那顆產品不能放行）。本模組把超規一律判 critical，
並在班末報告直接寫「立即隔離本班產出」。

## 預測性趨勢警告（本模組相對舊流程最大的價值）

對每條產線最近 `trend.window_shifts`（預設 6）個班別的不良率做**最小平方線性回歸**，
推算再幾個班次會撞上該線的 `defect_rate_limit_pct`：

| 預估剩餘班次 | 判定 | 依據 |
| --- | --- | --- |
| ≤ 3 班 | 🔴 critical | 書中「3–5 個班次前」的下緣，已迫在眉睫 |
| ≤ 5 班 | 🟠 major | 書中「3–5 個班次前」的上緣，正是處置成本最低的時機 |
| > 5 班 | 不發警報 | 超出預警視野，發了就是狼來了 |

斜率小於 `trend.min_slope_pct_per_shift`（預設 0.01 pp/班）視為雜訊，不做外推——
平的資料被浮點雜訊推出假預警，一週內就會讓廠長把預警當背景噪音。

mock 資料的 `L2 沖壓 B 線` 就是這個案例：不良率從 0.40% 一路走到 1.39%，
上限 2.00%，斜率約 +0.147 pp/班 → **預估約 4 個班次後撞線**，
在瑕疵實際產生之前發出 🟠 警告。同時跨班趨勢觸發 R3 / R5 / R6。

## 稽核軌跡（模組自帶，未改動 `_shared/`）

四階層報告鏈本身即品質稽核軌跡（apxG_p16），月報以 PDF Pack 形式歸檔。
`audit.py` 另外提供一份可持久化、可逐筆回溯的 **JSONL 稽核日誌**：

- 路徑優先序：`--audit-file` > 環境變數 `OPENCLAW_QC_AUDIT_LOG` > `config.yaml` > 模組預設
- 每一行帶 `prev_hash` / `entry_hash` 串成 **sha256 雜湊鏈**
- `audit.verify_file(path)` 可獨立驗證：任何一行被改動或抽掉都會在該行斷鏈
- 寫入失敗**不靜默吞掉**：計入 `write_failures` 並走 `Diagnostics.amber`。
  稽核軌跡寫不進去的那一次執行，在合規上等同沒發生

雜湊鏈不是為了防駭客（有寫入權的人可以整份重算），是為了防**無心的事後修飾**——
那在品管紀錄上是最常見、也最致命的一種資料失真。

記錄的事件：`run_started` / `mes_polled` / `alert_detected`（逐則）/
`tier_built`（**逐階記錄該階看見的全部警報 id，這就是「異常沒被吃掉」的證據**）/
`preflight` / `delivery` / `run_finished`。

## 全域安全閥：對外送出前的 `--dry-run` 內部通訊測試

依 apxG_p03 的 Level 3 全域要求「所有 API 呼叫前必經 `--dry-run` 內部通訊測試」，
`main.preflight()` 在任何對外送出**之前**執行一次不觸網的自我檢查：

1. 通道名稱合法且 `Notifier` 可建構
2. 該通道所需的憑證環境變數齊全（`CHANNEL_REQUIRED_ENV`）

任一項失敗 → 拒絕送出（`delivery.reason = "preflight_failed"`）並記琥珀燈，
而不是「先送送看再說」。console 通道視為本機列印，不受此閥與自主權閘門管制。

## 執行方式

```bash
# 零憑證、零網路，讀 mock/*.json 跑完整四階報告鏈
python main.py --mock

# 只產董事會報告包（PDF Pack 結構）
python main.py --mock --tier monthly

# 四階全出
python main.py --mock --tier all

# 跑完流程但不發送
python main.py --mock --dry-run

# 指定狀態檔與稽核檔位置（不污染模組目錄）
python main.py --mock --state-file /tmp/qc-state.json --audit-file /tmp/qc-audit.jsonl

# 注入固定基準時間與時區（供重現特定日期的報告）
python main.py --mock --as-of "2026-08-22T06:00:00+08:00" --timezone Asia/Taipei

# 串真實 API（缺憑證會列出缺哪些變數並退出，不會靜默退回 mock）
python main.py --live

# 測試
python -m pytest test_main.py -v
```

**exit code**：`0` 正常；`1` 設定或取數錯誤；`2` **報告鏈完整性檢查失敗**
（有警報在往上聚合時被吃掉——這種情況寧可不送）。

## 技術要點

- **數值全程 `Decimal`**：良率、不良率、公差、量測值一律 `Decimal(str(...))`。
  JSON 與 YAML 中的數值以字串儲存（`"1.50"`），避免 float 二進位誤差在跨班、
  跨週累加時被放大，讓稽核時對不起來。收斂用 `ROUND_HALF_UP`（品管慣例）。
- **百分比防零除**：分母為 0 一律回 `None`，顯示為「—」。**絕不回 0**。
- **時區用 `zoneinfo`**（禁 `pytz`）：`chain.timezone` 走 IANA 名稱。
  部分 Windows 環境缺 `tzdata` 時退回 `chain.utc_offset_hours` 的固定偏移並記琥珀燈——
  **不靜默改用 UTC**，那會讓 06:00 晨報整整早 8 小時送達而沒有人知道原因。
  測試以 `--as-of` + `--timezone` 注入固定時間與時區。
- **狀態檔 `--state-file`**：記錄各線最後處理班別與未結案警報，跨執行沿用。
- **稽核檔 `--audit-file`**：JSONL 雜湊鏈，見上方「稽核軌跡」。
- **路徑一律相對模組目錄**（`Path(__file__).resolve().parent`），不用 `cwd`——
  使用者從其他目錄執行時，狀態檔與稽核檔不會被丟進不相干的資料夾。
- **金鑰一律 `os.environ`**，無任何字串常數；`--live` 缺憑證走紅色警報退出。
- **依賴只有 PyYAML + pytest + 標準庫**：無 `requests`、**無任何 PDF 函式庫**。

### 為什麼不產生真正的 PDF

交付限制明訂不引入 PDF 函式庫。因此 Weekly / Monthly 的「PDF」與「PDF Pack」
**只輸出版面結構**：Markdown 本體 + `pdf_pack` 分冊清單（名稱／用途／內容），
交由下游排版服務渲染。`TierReport.output_format` 欄位會誠實寫明
「本模組輸出 PDF 版面結構，不產生 PDF 檔」。

## 已知限制

- MES 取數目前是 mock 讀檔；`--live` 的 Plex / SAP 真實 API client 尚未實作
  （`live.required_env` 已預留 `MES_PLEX_API_KEY` / `MES_SAP_API_KEY`）。
- 上週 / 上月基準值取自 `mock/history.json` 快照，未做真實的歷史資料庫查詢。
  基準缺項一律顯示「—」，**不以本期值回填**。
- 週報與月報只聚合自己期間內的班別（`chain._shifts_in`）；但 mock 資料僅涵蓋
  單一週次，跨週／跨月的分組邏輯尚未有真實資料驗證。
- `--tier shift_end` 或 `--tier all` 在 `--live` 下會對每一份報告各發一次 LLM 請求
  （mock 模式零成本）。正式部署建議四階各自排程，不要用 `all`。
- 排程本身由外部 cron / 排程器負責。建議 Daily 設 05:40 觸發，留 20 分鐘緩衝
  確保 06:00 前送達。
- 執行 `python main.py --mock` 會在模組目錄下建立 `state/` 與 `audit/`；
  若不希望產生，用 `--state-file` / `--audit-file` 指到別處，或加 `--no-audit`。
