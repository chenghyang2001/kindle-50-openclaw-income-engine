## 品質矩陣（對客戶的誠實揭露，不可省略）

**這張表必須在成交前給客戶看過。** 賣「100% 準確」會在第三週被打臉，
賣「這個區間 + 為什麼」則會建立長期信任。

| 逐字稿情境 | 判定 | 預期準確率 | 系統行為 |
| --- | --- | --- | --- |
| 結構良好、輪流發言、麥克風清晰 | `clear` | **85–92%** | 正常輸出，信心值 0.85–0.92 |
| 非正式、多人重疊、句子被打斷 | `messy` | **60–75%** | 信心值 ×0.8，輸出 amber 警示要求人工複核 |
| 有承諾但無人被指名 | 任一 | 承諾偵測不受影響 | `owner: null` + ⚠ 標示，**絕不猜測負責人** |

判定規則（`config.yaml` 的 `extraction`）：逐字稿標記 `quality_hint: messy`，
或重疊發言比例 > 15%，即歸入 `messy` 區間。

### 為什麼不追求更高的數字

本模組**只提取明確陳述的承諾**：`I will…`、`Can you…`、`我來處理`、`請你…`。
「我們之後應該要看一下定價」這種句子會被**丟棄**，不是漏抓，是刻意的設計。

放寬到模糊推論確實能讓「抓到的項目數」變好看，但代價是把「可能之後要做」
寫成客戶的待辦——一次捏造就足以讓整套系統失去信任。
**漏一項的代價，遠小於捏造一項。**

## 快速上手

```bash
# 零憑證、零網路，跑完整條流程（預設讀 mock/transcript_clear.json）
python main.py --mock

# 換一份逐字稿看不同品質區間的行為
python main.py --mock --transcript mock/transcript_messy.json
python main.py --mock --transcript mock/transcript_no_owner.json

# 跑完流程但不發送
python main.py --mock --dry-run

# 推到 Telegram
python main.py --mock --notify telegram

# 真實模式：啟動 Webhook 等待會議平台回呼（需 ANTHROPIC_API_KEY）
python main.py --live --serve --notify gmail

# 測試
python -m pytest test_main.py -v
```

### Webhook 接線（`--live --serve`）

```bash
curl -X POST http://127.0.0.1:8093/meeting-transcript \
  -H "Content-Type: application/json" \
  --data-binary @mock/transcript_clear.json
```

健康檢查：`GET /healthz`。伺服器以標準庫 `http.server` 實作
（不引入 Flask / FastAPI，維持 60 分鐘部署承諾），正式對外請放在
nginx / Cloudflare Tunnel 之後並加共享密鑰。

## 已知限制

- **不做日期推算**：只保留逐字稿裡出現的時間詞（`by Friday`、`週四前`）。
  跨時區把「Friday」算成錯誤日期，比留著原文更糟。
- **不做語者辨識**：負責人來自逐字稿的 speaker 標記與句中指名，
  會議平台若把兩個人合併成同一個語者，本模組無法補救。
- **不去重**：同一件事被兩人各自承諾會出現兩項，這是刻意的——
  合併是人的判斷，系統不該替客戶決定誰才是真正的負責人。
- **自主權預設 DRAFT**：要開 `supervised_auto` 必須提供白名單，
  且未滿 14 天會持續發出警告（書中鐵律）。
