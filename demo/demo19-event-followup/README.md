## 一、活動 ROI 是怎麼在沉默裡蒸發的

```
   活動當下                 +30 分鐘        +4 小時         +4 天
   ─────────                ────────        ───────        ──────
   ██████████ 意向強度      ████████        ████            █
   （剛聽完，記憶最鮮明）    （還記得你）     （開始模糊）    （已歸檔）
                                                             ↑
                                                    多數企業的第一封信
                                                    在這裡才寄出
```

**關鍵洞察**：活動的價值不在活動當天，而在**結束後那幾個小時**。
名單品質是全公司最高的（他們主動報名、主動出席、主動發問），
但它的半衰期以「小時」計算，不是以「天」計算。

本模組不是幫你辦更好的活動，而是**不讓已經辦好的活動白辦**。

## 三、與 demo10（客戶跟進序列）的差異 — 為什麼不能直接複用

兩個模組**表面上都叫「跟進序列」，但要解決的問題不同**，硬把 demo10 套上來會出事。

| 面向 | **demo10 — B2B 提案跟進** | **demo19 — 活動後跟進（本模組）** |
| --- | --- | --- |
| 對象 | **單一**已知決策者 | **一整份名單**（動輒數百人） |
| 已知條件 | 已有明確交易意向（都收到提案了） | **意向未明**，唯一線索是行為數據 |
| 序列數量 | **一條**（Day 3 / 7 / 14） | **三條**，先分群才知道走哪條 |
| 時間單位 | **天**（提案寄出 + N 天） | **分鐘**（活動結束 + N 分鐘）— 因為要求 30 分鐘內交棒 |
| 時間基準 | 每個人的 `proposal_sent_at` **各不相同** | 全體共用同一個 `event.ended_at` |
| 核心風險 | 誤發給已回覆的客戶 | 誤發給已回覆者 **＋ 對整份行銷名單的法遵責任** |
| 主要判斷 | 「這個案子還活著嗎」 | 「**這個人屬於哪一群**」 |
| 失敗模式 | 少跟進一次 → 少一個成交 | **分群錯誤 → 整批人被打擾** |

### 分眾邏輯才是這個模組的核心

demo10 不需要分群，因為只有一個人。本模組**分群錯了，後面文案寫得再好都是打擾**：
把只看了 15 分鐘的人當成高意向直接約會議，比不寄信更傷。

| 分群 | 判定條件（書中規格） | 序列節奏 | 訴求主軸 | 業務交棒 |
| --- | --- | --- | --- | --- |
| **hot**（Fully Engaged） | 出席 **> 80%** **且**有互動訊號 | +30 分鐘 → Day 1 → Day 3 | 引用其提問 → 約 20 分鐘會議 → 體面收尾 | ✅ **30 分鐘內** |
| **warm**（Attended） | 出席 **40–79%** | +2 小時 → Day 2 → Day 5 | 補完錄影 → 給可自己做的小步驟 → 低壓力邀請 | ❌ |
| **cold**（Registered Only） | 未出席或出席 **< 40%** | +4 小時 → Day 3 | 無責備地補送錄影 → 邀下一場後退場 | ❌ |

**互動訊號**（`segmentation.engagement_signals`）：任一成立即算有互動。
書中原文只點名「**發問**」；本實作額外納入「**下載資料**」——兩者都是主動行為，
且在沒有 Q&A 環節的錄播型活動裡，下載是唯一可得的互動訊號。此清單放在 config，
客戶若堅持只認發問，改設定即可，不必動程式。

**規格留白處的處理（明確記錄，不假裝書中有寫）**：
書中把 Fully Engaged 定義為「出席 > 80% **且**發問」，`Attended` 定義為「40–79%」，
但**沒有定義「出席 90% 卻全程沉默」該去哪**。本實作讓他自然落入下一個門檻較低的
分群（warm），而不是另立第四群。理由：這種人的意向強度確實介於兩者之間，
硬給 hot 會浪費業務人力，而業務人力是這條流程裡最貴的資源。

## 四、兩個不可停用的安全開關

本模組有**兩條**規則的優先權高於排程、高於自主權設定、高於任何客製需求。
兩者都在 `EventFollowUpSequencer` 建構子被**強制覆寫為 `True`**，
config 改成 `false` 只會換來一則 AMBER 警告，不會改變行為。

### 4-1 `stop_on_reply` — 回覆即中止

失敗代價是不對稱的：

| 失敗方向 | 後果 | 可逆性 |
| --- | --- | --- |
| 少發一封跟進 | 損失一次接觸機會 | 可逆（下次補寄即可） |
| 發給已回覆的人 | 「我明明回你了」「這是機器人吧」 | **不可逆**（信任一旦破壞無法收回） |

而且誤發往往正好發生在**對方剛表達興趣**的當下——也就是價值最高的那一刻。

### 4-2 `respect_unsubscribe` — 退訂即永久排除

活動名單屬於**行銷聯繫**，不是既有客戶的交易通訊。忽視退訂不是體驗問題，
是**法遵事故**（台灣《個資法》第 20 條、GDPR Art. 21、美國 CAN-SPAM）。
因此本模組把退訂與回覆放在同一個層級：不可由設定關閉。

### 實作上的兩道閘門

```
排程判定                            實際發送前
────────                            ──────────
sequencer.plan()                    sequencer.assert_can_send()
  → has_replied() 檢查                → has_replied() 再檢查一次
  → is_unsubscribed() 檢查            → is_unsubscribed() 再檢查一次
  → 分群 + 到期判定
                  ↓ 中間隔著整份名單的 LLM 產文時間
                    300 人的名單跑完可能要數十分鐘，
                    這段空窗有人回信或按退訂是常態而非例外
```

**只在排程時檢查一次是不夠的**。正式環境可對 `assert_can_send()` 傳入
`reply_checker` / `unsubscribe_checker`，改成即時查 CRM、收件匣與退訂中心，
而不是沿用排程當下的快照。

### 判定採「寬鬆」策略

以下**任一**訊號成立即中止：

- **已回覆**：`has_replied == true`／`replied_at` 有值／`status == "replied"`
- **已退訂**：`is_unsubscribed == true`／`unsubscribed_at` 有值／`status ∈ {unsubscribed, opted_out}`

寧可少發一封，也不要誤發。

## 五、法遵：行銷名單信件的三件套（部署前必讀）

活動名單是**行銷聯繫**，每一封信都必須可識別、可退出。本模組把三件套寫進
`config.yaml` 的 `compliance` 區段，**缺任何一項就把當次全部信件強制降為草稿**
（禁止自動送出）並發出 AMBER：

| 欄位 | 用途 | 缺了會怎樣 |
| --- | --- | --- |
| `sender_identity` | 寄件人可識別：公司全名 + 具名負責人 | 無法識別寄件人 → 高機率被歸類為垃圾信 |
| `physical_address` | 實體通訊地址 | CAN-SPAM 明文要求；缺少即違法 |
| `unsubscribe_url` | 一鍵退訂連結（含 `{{ATTENDEE_TOKEN}}` 佔位符） | **最嚴重**——沒有退訂出口，對方只剩「檢舉垃圾信」一條路 |
| `unsubscribe_token_salt` | 產生退訂 token 的 salt | 沒有 salt，任何人知道 email 就能算出別人的 token 並代為退訂 |
| `reply_to` | 可回信的真實信箱 | 用 `no-reply@` 等同告訴對方「不想聽你說話」 |

信尾由 `_compliance_footer()` 統一組出並附加在每一封信的末端，**不交給 LLM 生成**
——法遵資訊必須逐字可控，不能讓模型改寫或漏寫。

### 退訂 token：為什麼不能全名單共用一組連結

`unsubscribe_url` 中的 `{{ATTENDEE_TOKEN}}` 會被 `_compliance_footer()` **逐封替換**成
該與會者專屬的 token：

```
token = sha256(f"{salt}:{email.lower()}").hexdigest()[:16]
```

| 設計選擇 | 理由 |
| --- | --- |
| **不把 email 直接放進網址** | 退訂連結會出現在信件內文、瀏覽器歷史、referer 與伺服器 access log —— 明文 email 等於把整份名單沿路灑出去，退訂機制反而變成個資外洩管道 |
| **加 salt** | 沒有 salt，任何人知道 email 就能自行算出 token，替別人退訂或列舉名單 |
| **取 sha256 前 16 碼** | 足以避免碰撞，又短到能塞進網址不破版；無法反推回 email |
| **同一人每次執行 token 相同** | token 必須穩定，否則舊信裡的退訂連結會在下次執行後失效 |

**替換後仍殘留 `{{` 的信件會被強制降為草稿**，並發出 AMBER。理由：一個點不動的
退訂連結**比完全沒有連結更危險**——沒有連結一眼就看得出不合規；壞掉的連結外觀合規、
實際失效，往往要等到收到客訴或檢舉才會發現。

> ⚠️ **正式部署必做**：`config.yaml` 內附的 salt 是**示範值**且已進版控。
> 部署時務必改為 `unsubscribe_token_salt: "${OPENCLAW_UNSUBSCRIBE_SALT}"`
> （`_shared/config_loader.py` 會自環境變數展開），並把真實 salt 當作機密管理。
> 跑 `--live` 時若偵測到仍是示範值，程式會發出 AMBER 警告。
> **salt 一旦更換，所有已寄出信件裡的舊退訂連結都會失效**，換 salt 前請先評估。

**其餘提醒（本模組未實作，部署時需補）**：

1. 退訂端點必須**真的能運作**且**即時生效**：用 token 反查名單、標記退訂、
   回寫名單來源（CRM / 活動平台），否則下一場活動又會把人抓回來。
2. 退訂應為**一鍵完成**，不得要求登入或填問卷。
3. 名單來源要留存**報名同意紀錄**（時間、IP、同意條款版本），以備稽核。
4. 跨境活動（歐盟與會者）需在報名表就取得明示同意，不可事後補。

## 六、CRM 交棒：30 分鐘 SLA

書中規格明寫：**活動結束 30 分鐘內**把高熱度名單送到業務 Slack。
本模組把它做成可稽核的 SLA，而不是「盡快」：

- 期限 = `event.ended_at` + `crm.handover_deadline_minutes`（預設 30）
- 每筆交棒記錄 `deadline_at` / `dispatched_at` / `is_within_sla`
- **逾時仍然交棒**（遲到的線索還是線索），但同時發出 AMBER 並寫入 `warnings`
- 已交棒過的人不會被重複推進（`crm_handover_done` 或狀態檔任一為真即跳過）

交棒卡片內容：姓名、公司、職稱、Email、出席比例、**原始提問逐字**、lead score。
業務拿到的不是一個 Email，是**一句可以直接開場的話**。

> ⚠️ mock 資料的基準時間刻意設在活動結束 **3.5 天後**（為了讓三條序列的多個段落
> 在同一次執行中同時到期，方便驗證），因此 `python main.py --mock` 會如實顯示
> 一筆「交棒逾時」的 AMBER。**這是預期行為，不是 bug**——它示範的正是 SLA 告警路徑。

## 九、Client Pitch（銷售話術）

**原文（投影片逐字）**：

> 「Every attendee gets the right follow-up at the right time... and automatically
> handed to your sales team within the hour.」

**繁體中文翻譯**：

> 「每一位與會者都會在正確的時間收到正確的跟進……而且會在一小時內自動交到您的
> 業務團隊手上。」

**話術補充（現場對答用）**

| 客戶疑慮 | 回應 |
| --- | --- |
| 「一封感謝信寄給全部人不就好了？」 | 那正是現在的做法，也是為什麼活動 ROI 算不出來。全程參與又發問的人，跟只看了 10 分鐘的人，需要的是完全不同的下一步。同一封信對兩邊都不對。 |
| 「4 天後再寄有差嗎？」 | 這份名單的半衰期以小時計。活動結束 30 分鐘內他還記得自己問過什麼；第 4 天他連活動名稱都要想一下。我們把最有價值的那 30 分鐘拿回來。 |
| 「萬一有人已經回信了怎麼辦？」 | 這是優先權最高的安全機制。系統在**每一封信送出前**都會再查一次回覆與退訂，只要偵測到，該人的整條序列立即中止，而且**這個開關不能被設定關掉**。 |
| 「會不會被當成垃圾信？」 | 每封信都有具名負責人、實體地址與一鍵退訂——缺任何一項，系統會直接拒絕自動送出、全部轉為草稿。書中數據也顯示具名寄件可提升 30–40% 回覆率。 |
| 「業務會看那個 Slack 頻道嗎？」 | 我們送過去的不是一個 Email，是姓名、公司、出席比例，加上**他在現場逐字問了什麼**。業務不需要準備開場白，那句話就是開場白。 |
| 「$240 會不會太貴？」 | 以每月一場活動、回收 20 小時計算，光是人力就值 $1,600。這還沒算轉換率 3–4 倍的部分。 |

## 十、使用方式

```bash
# 離線跑完整流程（零憑證、零網路、零副作用）
python main.py --mock

# 推到 Telegram
python main.py --mock --notify telegram

# 跑完流程但完全不發送（狀態檔也不會被寫入）
python main.py --mock --dry-run
```

### 狀態檔規則（`--state-file`）

| 情境 | 讀狀態檔 | 寫狀態檔 |
| --- | --- | --- |
| `--mock`（未指定 `--state-file`） | ❌ | ❌ |
| `--mock --state-file <path>` | ✅ | ✅ |
| `--mock --state-file <path> --dry-run` | ✅ | ❌ |
| `--live` | ✅ | ✅ |
| `--live --dry-run` | ✅ | ❌ |

**為什麼預設 `--mock` 完全不碰檔案**：讓 `python main.py --mock` 每次執行的結果
一模一樣，QA 可重複驗證，也不會在 repo 裡留下垃圾。

狀態檔內含 `event_id`。若拿 A 活動的狀態檔跑 B 活動，程式會**直接拒絕執行**
並提示改用 `--state-file`——跨活動污染會讓整批人漏收信，比報錯嚴重得多。

## 十二、已知限制

- **本 demo 不含 CRM / Slack 實際寫入**。`crm_handovers` 只產出結構化卡片內容，
  正式部署需接 Slack Webhook 與 CRM API，並把 `sent` 結果回寫，
  否則下次執行只能依賴本機狀態檔判斷已送出項目。
- **回覆與退訂偵測在 mock 模式讀的是 `attendees.json` 快照**。正式環境務必對
  `assert_can_send()` 傳入 `reply_checker` / `unsubscribe_checker`，改為即時查詢。
- **退訂 token 已個人化，但退訂端點本身未實作**。每封信的 `{{ATTENDEE_TOKEN}}` 都會被
  替換成該與會者專屬的 `sha256(salt:email)` 前 16 碼，但 `https://example.com/unsubscribe`
  是示範網址；正式部署必須自行實作「用 token 反查名單 → 標記退訂 → 回寫來源系統」
  的端點，並把 salt 改為環境變數（見第五節）。
- **無寄送速率控制**。數百人的名單一次送出容易觸發郵件服務商的節流或信譽扣分，
  正式部署需加入分批與間隔（參考 `_shared/notifier.py` 的分段機制）。
- **序列僅支援單一語言版本**。多語系活動需為每個語言複製一組 `prompts/`。
- **分群門檻是靜態的**。書中未提供依活動類型（如 30 分鐘快閃 vs 3 小時工作坊）
  調整門檻的方法；目前需人工在 `config.yaml` 依活動長度調整 `min_attendance_pct`。
