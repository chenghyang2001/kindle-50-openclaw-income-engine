# demo17 — 每週績效儀表板（Weekly Performance Dashboard）

> 模組 #17 ｜ Level 2 代理商基礎 ｜ 分類：營運法務 / 後台風險
> 部署 **5–6 小時（全書最高複雜度）** ｜ 客戶每月回收 **12 hrs**
> 定價 **$1,200 首付 + $250/月**

Agent 每週一早上自動連接 **GA4 / Google Ads / Meta / CRM / Xero / QuickBooks** 六套系統，
依 `METRICS_MAP` 取出每個區塊 4–5 個關鍵 KPI，計算**週對週（WoW）變化**與**四週移動平均**，
用 **RAG 燈號**標出狀態、用 **15% 門檻**標出異常，最後附上 **3 個基於數據的本週行動建議**，
在 **07:00** 送到管理層信箱。

本實作**一律採用附錄 F**，理由是：**附錄 F 是逐模組的技術與商業規格表**（Input / Processing /

規格衝突時採信規格表，是可辯護的預設；但兩邊的數字都如實列在下面，不做平均、不做隱藏。

| 衝突項 | 第 05 章 | 附錄 F | **本實作採用** | 落在哪裡 |
| --- | --- | --- | --- | --- |
| 客戶定價 | $850 設置費 + $220/月 | **$1,200 首付 + $250/月** | **附錄 F** | `config.yaml` → `module.client_setup_price` / `client_monthly_price` |

### 為什麼「發送時點」要做成可設定，而不是寫死週一

因為這個衝突不只是文字差異，它連帶推翻了第 05 章的一項效益宣稱：

> 第 05 章：「讓管理層提早 **60 小時**獲得決策數據（週五 vs 週一）」

那 60 小時**正是「週五 18:00 送」相對「週一 07:00 送」的差額**。
一旦採用附錄 F 的週一 07:00，這 60 小時的效益就不存在了——兩個來源在這裡是真的互斥，
不可能同時成立。本實作的處理是：

- 預設照附錄 F 走 **週一 07:00**（`deliver_day: monday` / `deliver_at: "07:00"`）。
- 但把兩個欄位都放進 `config.yaml`，客戶想要第 05 章那套（週五 18:00、換取提早 60 小時）
  只要改設定，不必改程式碼。不同客戶的週會時間本來就不同，寫死在原始碼裡等於逼每個客戶
  各分叉一份程式。

**本 README 的財務模型不把那 60 小時計入效益**，因為我們採用的是週一版本。
把互斥來源的好處各取一半加總，是這類商業文件最常見的謊。

## 為什麼要有「部分失敗」設計（本模組最重要的決策）

六個資料源是全書之最，這代表**任一週有某個源掛掉，幾乎是常態而不是例外**。
一般做法是取不到就中止、寄錯誤信給工程師。**這個模組刻意不那樣做。**

1. **整份失敗會讓 Agent 重現它要消滅的舊狀態。**
   客戶買的價值是「週會不用再現場組資料」。Meta 掛掉那週如果整份不發，管理層就退回到
   憑印象開會——跟導入前一模一樣，還多了一份被辜負的期待。**六分之五的數字仍有決策價值。**

2. **殘缺數據的真正風險不是「不完整」，而是「看起來完整」。**
   所以缺資料時的處理是**加標記**，不是**補數字**：
   - 報表最上方強制加橫幅：`⚠️ 部分資料：Meta Ads 無回應`
   - 橫幅下一行明寫「請勿據此調整預算或究責」
   - 故障源負責的 KPI **仍然列在區塊裡**，標成 `⚪ 無資料 —— Meta Ads 無回應`，
     不會從畫面上消失（**消失的指標沒有人會發現它消失了**）
   - 該區塊標記 `（部分資料）`，燈號不會因為少了兩個 KPI 就變綠
   - 提示詞（`prompts/dashboard.md`）明令 AI **不得推估、補值或杜撰**缺失數字

3. **維運端仍然必須被通知。**「照常發出」不等於「假裝沒事」。
   每個失敗源都會走 `Diagnostics.amber(symptom, fix)` 進入 RAG 診斷矩陣的琥珀燈：
   流程繼續、但留下明確的症狀與修法。只有系統性失效才走紅燈退出
   （例如 `--live` 缺憑證——這種情況寧可不跑，也不能靜默降級成 mock）。

一句話：**降級，但絕不假裝。**

## 為什麼「首週」要單獨設計

週報的靈魂是比較，而每個客戶都必然有一週**沒有東西可比較**。這一週最容易出兩種錯：

| 錯誤做法 | 後果 |
| --- | --- |
| 把上週值當成 `0` 去算 | 每個指標都變成「成長 +100%」或直接除零爆掉，第一份報表就在說謊 |
| 把沒有基準的指標塗成綠燈 | 灰燈（不知道）被當成綠燈（正常），管理層以為一切良好 |

本實作的處理：

- `percent_change()` 的分母為 0 或任一端缺值，一律回 **`None`**，永遠不回 `0%`。
- 燈號有第四種狀態 **`unknown`（⚪ 無比較基準）**，在報表與 JSON 中都與 `green` 明確區分。
- **Focus Actions 留空**：沒有趨勢就不編建議，報表直接寫
  「首週或無可比較資料，本週不提出以趨勢為依據的建議」。
- 報表抬頭明寫「比較基準：無——本週為首次執行，所有週對週比較留空，不以 0 代替」。
- 首週跑完會把本週值寫進狀態檔當**基準線**，下週就有得比了。

第二週起（歷史只有 1 週）也不會被擋下：四週移動平均**不要求湊滿四週**，
有幾週算幾週，樣本數以 `history_weeks` 一併交給提示詞說明。

## 異常標記與 RAG 燈號規則

門檻**全部**寫在 `config.yaml` 的 `thresholds`，程式碼中沒有任何寫死的數字。

| 規則 | 預設門檻 | 設定鍵 | 為什麼 |
| --- | --- | --- | --- |
| 異常標記 | 週對週變動絕對值 **> 15%** | `anomaly_pct` | 附錄 F 的 `ANOMALY_THRESHOLD` 預設值 |
| 🟡 黃燈 | 對客戶**不利**方向變動 **≥ 5%** | `rag_amber_pct` | 值得在週會上提一句 |
| 🔴 紅燈 | 對客戶**不利**方向變動 **≥ 15%** | `rag_red_pct` | 需要當週處理，不是月底再說 |
| ⚪ 灰燈 | 無比較基準（首週 / 資料源故障） | — | 不知道就是不知道，不塗成綠色 |
| KPI 數量上限 | 每區塊 **5 個** | `max_kpis_per_block` | 書中規定 4–5 個；超過就截斷 + 記琥珀燈 |

### 「異常」不等於「壞消息」

每個 KPI 都有 `direction` 欄位：`up`（越高越好，如營收、ROAS）或 `down`（越低越好，
如廣告花費、每筆名單成本、平均成交天數）。異常標記看的是**變動幅度**，燈號看的是**方向**。

所以在 mock 的正常週裡會同時出現這兩條：

- `google_ads_spend` +20% → **異常 ⚠️ + 紅燈 🔴**（花費暴增，方向不利）
- `crm_new_leads` +20% → **異常 ⚠️ + 綠燈 🟢**（名單暴增，方向有利）

後者一樣要標異常——名單一週跳 20% 通常是活動檔期或**追蹤碼重複觸發**，兩種都需要人看一眼。
把「異常」直接等同於「壞事」，會讓最重要的資料品質問題永遠被忽略。

### 為什麼上限是截斷而不是拒絕執行

`max_kpis_per_block` 被超過時，程式**截斷到前 5 個並記琥珀燈**，不拋錯。
書中這條限制的目的是保住可讀性，不是資料正確性；多塞了兩個 KPI 就整份報表不發，
等於用更大的傷害去糾正一個排版問題。

## Focus Actions：挑選由數學決定，措辭才交給 AI

附錄 F 要求「3 個基於數據的本週行動建議」。本實作把它拆成兩層：

1. **挑選**：`select_focus_actions()` 把所有 KPI 依「對客戶最不利的變化幅度」升冪排序，
   取前 3 個。同分時靠 Python 的穩定排序維持 `config.yaml` 的區塊順序。
   → **同樣的輸入永遠得到同樣的三條建議。**
2. **措辭**：把這 3 個 KPI 交給 `prompts/focus-actions.md`，由 LLM 寫成可執行的句子。
   提示詞第一條規則就是「**不要自己挑指標**」。

為什麼要這樣切：讓模型自己挑重點，同一份數字每週會得到不同的優先順序，
客戶第三週就會發現「上週你說要顧 ROAS，這週怎麼不提了」——報表的信任會在那一刻結束。

## 週對週比較的歷史從哪裡來

WoW 與四週移動平均需要歷史值，本模組用**狀態檔**保存：

| 情境 | 讀 | 寫 |
| --- | --- | --- |
| `python main.py --mock`（未給 `--state-file`） | `mock/history.json`（唯讀種子，4 週） | **不寫任何檔案** |
| `python main.py --state-file <路徑>`（檔案已存在） | 該狀態檔 | 跑完寫回該狀態檔 |
| `python main.py --state-file <路徑>`（檔案不存在） | 退回 `mock/history.json` | 建立該狀態檔 |
| 加了 `--dry-run` | 同上 | **不寫**（dry-run 不該有副作用） |

這個兩段式是刻意的：`--mock` 是給人隨手驗證流程用的，跑一次就把版控中的
`mock/history.json` 寫髒，等於每次 demo 完都要 `git checkout`。真正部署時再指定
`--state-file` 到一個持久路徑（例如 `~/.openclaw/demo17-state.json`）。

其他兩個設計：

- **同週次重跑會覆寫而不是新增**。週一早上因為某個源掛掉而重跑三次，不該在歷史裡留下
  三筆 `2026-W33`，否則四週移動平均會被同一週灌爆。
- **狀態檔只留最近 `keep_weeks`（預設 12）週**，避免無限增長。
- **寫不進狀態檔不會讓已算好的報表作廢**：記琥珀燈、報表照發，代價是下週少一個比較基準。

## 財務模型（Financial Model）

採附錄 F 定價。時薪以 **$75/hr** 估算（與本系列其他模組一致）。

| 項目 | 數值 |
| --- | --- |
| 部署時間 | **5–6 小時**（全書最高複雜度） |
| 客戶每月回收 | **12 hrs/mo**（原 2–3 小時 × 4–5 週） |
| 回收價值 | **$900 /mo**（12 hr × $75） |
| 建置費（Setup） | **$1,200** |
| 月費 | **$250 /mo** |
| 客戶第一個月成本 | $1,450 |
| 客戶第一個月淨值 | **−$550** |
| 客戶每月穩定淨值（第 2 個月起） | **+$650 /mo** |
| 投資回收期 | **約 7 週**（累計淨值於第 2 個月轉正） |
| 客戶年度淨值 | $10,800 − $4,200 = **+$6,600** |

**這個模組的第一個月是負的**，這點必須在銷售時直說。它跟 #13 客戶入職（$180/mo、
2 小時內部署）不是同一類商品：#17 是**深度配置的利潤中心**，附錄 F 的商業決策矩陣
把它和 #18 合約審查一起放在「深度配置（5–6 hrs）」象限。第 7 週轉正、年度 +$6,600
才是它的賣點，用「第一個月就回本」去賣它會在第 30 天被拆穿。

供給端（你）：部署一次 5–6 小時，之後每月 $250 近乎純被動收入。
接 10 個客戶 = **$2,500/mo** 經常性收入。維護成本集中在六個資料源的憑證到期
（OAuth token、API key 輪替），這也是為什麼「部分失敗」設計不是加分項而是必要項——
沒有它，每一次憑證過期都會變成一次客訴。

## 執行方式

```bash
# 零憑證、零網路，讀 mock/*.json 跑完整流程（不會寫任何檔案）
python main.py --mock

# 推到 Telegram
python main.py --mock --notify telegram

# 跑完流程但不發送、不寫狀態檔
python main.py --mock --dry-run

# 累積歷史：優先讀該檔，跑完寫回該檔
python main.py --mock --state-file ~/.openclaw/demo17-state.json

# 串真實 API（缺憑證會列出缺哪些變數並退出，不會靜默退回 mock）
python main.py --live

# 測試
python -m pytest test_main.py -v
```

### 重現三種情境

| 情境 | 做法 |
| --- | --- |
| 正常週 | 直接 `python main.py --mock`（預設） |
| 某源故障週 | 把 `config.yaml` 的 `sources[meta].mock_file` 改成 `mock/meta-outage.json` |
| 首週（無歷史） | 把 `config.yaml` 的 `history.mock_file` 改成 `mock/history-first-week.json` |

三種情境都各有一個對應的測試（`test_main.py`），不改設定也驗得到。

```
│   └── focus-actions.md         # 把已排序的重點 KPI 寫成 3 個行動建議
├── mock/
│   ├── ga4.json                 # 流量與轉換
│   ├── google-ads.json          # 花費 / CPL / ROAS（本週 +20%，觸發紅燈與異常）
│   ├── meta.json                # 花費 / CTR
│   ├── meta-outage.json         # 「某源故障週」情境：帶 error 欄位

```

### 為什麼六個資料源共用一個 fetcher，而不是六支模組

因為在 `--mock` 這層，六個平台的 payload 形狀完全相同（`{"metrics": {...}}`）——
為每個平台各寫一支只差檔名的模組是純粹的重複。`--live` 時各平台 API 的差異
（GA4 的 Data API、Meta 的 Graph API、Xero 的 OAuth 2.0…）應該收斂在
「回傳 `{metric_key: 值}`」這層介面之後，`fetch_source()` 以下的所有邏輯完全不必改。

（對照組：demo09 為三個資料源各寫一支模組，是因為它們的原始 payload 結構天差地別
——CRM 要加總 `closed_won`、Shopify 要扣退款、Stripe 要扣手續費，那些差異無法共用。）

### METRICS_MAP 的四個區塊

| 區塊 | KPI 數 | 資料源 | 涵蓋 |
| --- | --- | --- | --- |
| 流量與轉換 | 4 | GA4 | 工作階段、不重複使用者、轉換率、平均停留時間 |
| 廣告投放 | 5 | Google Ads + Meta | 兩平台花費、每筆名單成本、ROAS、點擊率 |
| 銷售管線 | 5 | CRM | 新增名單、合格商機、管線總值、成交率、平均成交天數 |
| 財務營收 | 4 | Xero + QuickBooks | 營收、毛利率、支出、現金餘額 |

**KPI 綁的是資料源，不是區塊。** 這代表 Meta 掛掉時，「廣告投放」區塊會標成
`（部分資料）`，但 Google Ads 那三個 KPI 照常計算與上燈號——不是整個區塊一起陣亡。

## 技術要點

- **數值全程 `Decimal`**：JSON 與 YAML 的數值一律以字串儲存（`"4800.00"`），
  避免 float 二進位誤差在百分比與四週移動平均上被反覆放大，
  讓 15.0% 的門檻在邊界上隨機翻面。收斂用 `ROUND_HALF_UP`（財務慣例）。
- **除以零防禦**：`percent_change()` 的分母為 0 或任一端缺值一律回 `None`，
  **絕不回 `0%`**。這條規則同時擋掉「首週」與「上週該指標為 0」兩種情境。
- **自主權階梯**：報表會寄給客戶管理層，依第 04 章鐵律預設 `draft`。
  非 console 通道要真的送出，需 `supervised_auto` + 非空白名單 + 連續穩定 14 天。
  console 通道視為本機列印，不受閘門管制。
- **設定錯誤不靜默**：`deliver_at` / `deliver_day` 格式錯誤直接拋錯，不悄悄套用預設值——
  否則「為什麼週報沒在我設定的時間送出」會變成無解懸案。
- **週次不一致會告警**：六個源各自回報 `week_id`，取多數決；有源回報不同週次時記琥珀燈。
  這通常代表某個平台（多半是財務系統）當週還沒結算完，把兩週的數字混在一起做 WoW，
  會產生看起來合理但完全錯誤的趨勢。
- **`run()` 回傳鍵名**：同時提供契約 §6「未來標準化」建議的六個鍵
  （`module_id` / `module_name` / `mode` / `dry_run` / `warnings` / `amber_count`）
  與本模組專屬欄位，讓 `bundle-quickstart/run_all.py` 的轉接層不必再猜。

## 已知限制

- 六個資料源目前都是 mock 讀檔；`--live` 的真實 API 串接需補上各平台的 client
  （GA4 Data API / Google Ads API / Meta Graph API / CRM / Xero / QuickBooks，
  各自的 OAuth 流程是這個模組「5–6 小時、最高複雜度」的主要來源）。
- 附錄 F 的 Output 寫「**PDF** + Slack」，本實作只產出純文字 + `_shared.notifier` 的
  五個通道（console / telegram / gmail / line / whatsapp）。PDF 排版需要額外的第三方
  套件，超出契約 §0「只允許 PyYAML + pytest」的依賴限制，故未實作。
- 四週移動平均取自狀態檔的快照，未做真實的資料倉儲查詢；`keep_weeks` 到期後的歷史
  會被裁掉，若要做季度或年度趨勢需另接資料庫。
- 時區僅用於報表顯示，實際排程由外部 cron / 排程器負責
  （建議設週一 06:30 觸發，留 30 分鐘緩衝，確保 07:00 前送達）。
