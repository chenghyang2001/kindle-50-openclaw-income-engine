## 1. Before / After

| 階段 | Before（人工） | After（Agent） |
| --- | --- | --- |
| 寄出 PO | 郵件發送後存進「已寄件」，然後忘記 | ERP 的未結 PO 每天被完整掃過一次 |
| 追蹤確認 | 憑印象「好像有回吧」 | 24 小時內沒有**有效**確認就進催辦名單 |
| 追蹤交期 | 等對方主動通知，通常等不到 | 交期前 48 小時自動追蹤，交期後 24 小時判逾期 |
| 供應商回覆 | 混在幾百封信裡，看到才算 | PO 號碼 + 寄件網域雙重比對，再分類為確認／出貨／到貨／延遲／發票 |
| 讀不懂的回覆 | 當成「這張沒動靜」 | **明確警報**：讀不懂 ≠ 沒有更新 |
| 議價籌碼 | 「他們好像常常遲到」 | 每月計分卡：準時率 + 平均確認時數，附單號可查 |
| 發現問題的時機 | 生產線停工當天 | 逾期的第一個小時 |

### 架構：Input / Processing / Output（附錄F apxF_p14）

```
[Input]                    [Processing]                       [Output]
orders@ 信箱  ──┐                                        ┌──► 催辦信草稿（預設不自動寄）
                ├──►  Email Match（PO 號碼 + 寄件網域）  ├──► ERP 狀態更新
ERP / Xero    ──┘         │                              ├──► 未結金額（依幣別分列）
（未結 PO）               ├─ Classification 分類 5 類     └──► 每月供應商計分卡
                          │    └─ 分不出來 ──► AMBER 警報
                          ├─ 狀態機：下單→確認→出貨→到貨
                          │    └─ 倒退事件 ──► AMBER，不改階段
                          └─ Chaser Logic：逾期判定 + 冷卻期
```

**先比對再分類**，順序不可對調：一封「內容看起來像確認、但寄件人不是這家供應商」的信，
必須在進入狀態機**之前**就被擋下（`mock/supplier_replies.json` 的 `e005` 就是這個案例）。

## 2. 安全設計（為什麼這個模組敢自動寫催貨信）

| 閘門 | 行為 |
| --- | --- |
| **自主權階梯** | 催辦信是寄給供應商的**對外信件**，預設 `draft`：只印在本機等採購過目。要自動送出必須填 `approved_senders` 白名單，且書中鐵律要求先跑滿 14 天草稿（未滿會留 AMBER） |
| **語氣分級** | `prompts/chaser_email.md` 依警報嚴重度分四級語氣，最嚴重的逾期也禁止出現責備、違約金、法律行動等字眼——那是採購主管親自談判的事 |
| **網域比對** | 供應商網域必須以 `@` 開頭做結尾比對。裸網域會讓 `sales@fake-delta-circuit.example` 誤判命中，冒名者只要註冊含目標網域的網域名就能把假的「已確認」寫進狀態機 |
| **解析失敗必警報** | 讀不懂的回覆一律轉 AMBER 並列進報告，**絕不當成「這張 PO 沒有更新」** |
| **狀態只准前進** | 錯序的郵件不會把 PO 打回上一段；倒退事件記為異常並發 AMBER |
| **金額精度** | 全程 `decimal.Decimal`；**不同幣別絕不相加**，沒有匯率就不做換算 |
| **催辦冷卻期** | 同一張 PO 在 `chaser_cooldown_hours`（預設 48 小時）內不重複催，避免每日排程轟炸供應商 |

## 3. Financial Model

### 客戶端（單一客戶，12 個月）

| 項目 | 金額 |
| --- | --- |
| 建置費（一次） | $1,000 |
| 月費 × 12 | $3,240 |
| **客戶總支出** | **$4,240** |
| 回收產能 78 hrs/mo × $60/hr × 12 | $56,160 |
| **淨效益** | **$51,920** |
| **ROI** | **約 1,225%** |

- 78 hrs/mo 由書中「每週回收 18 小時」× 4.33 週換算。
- 首月：成本 $1,270 vs 價值 $4,680 → **第 9 天左右即回本**。
- 第 2 個月起：成本 $270 vs 價值 $4,680 → 每月淨賺 **$4,410**。

> **口徑說明**：18 hrs/week 是書中的客戶端價值主張數字，實務上多數中小企業的採購
> 不會有這麼多純追蹤工時。這個模組真正的價值不在工時，而在書中的另一句話：
> **缺貨事件減少 60-80%**。一次因為零件晚到而停線的損失，通常就超過這套系統一整年的服務費。

### 服務商端

| 客戶數 | 一次性建置收入 | MRR | 年營收 |
| --- | --- | --- | --- |
| 5 | $5,000 | $1,350 | $21,200 |
| 10 | $10,000 | $2,700 | $42,400 |
| 25 | $25,000 | $6,750 | $106,000 |

部署 1 Day，主要工作是：串 ERP 的未結 PO 端點、接上 `orders@` 信箱、
把客戶前 20 家供應商的網域填進名冊。之後的維護幾乎只剩「新供應商的信件範本沒被分類到」——
而那件事本模組會自己警報，不用等客戶來抱怨。

## 5. Client Pitch

### 原文（apxF_p14）

> 「Every purchase order tracked from send to delivery... late deliveries flagged before
> they become production problems.」

### 繁體中文翻譯

> 「每一張採購單，從寄出到交付全程被追蹤……延遲交貨在變成生產問題之前，就先被標記出來。」

### 話術展開

**開場**：你上一次發現某張採購單出問題，是自己查到的，還是產線主管跑來跟你說沒料了？

**痛點**（書中原文）：
> 「採購訂單寄出後往往被遺忘，直到生產線停工才發現零件晚了。
> 供應鏈透明度對中小企業來說攸關生死。」

**方案**：$1,000 建置、$270/月。每天早上，你會拿到一份清單：
哪幾張 PO 逾期、逾期幾小時、催辦信草稿已經寫好在下面，看過按送出就好。

**升級點**：跑滿一季之後，你手上會多一份東西——每月供應商計分卡。
下次議價時，「你們常常遲到」變成「貴司本季準時率 0%，平均確認時間 25.5 小時」。
**這才是這個模組真正貴的地方。**

**風險反轉**：第一個月照跑，如果一次有效的逾期警報都沒有，退費。
（實務上不會發生——只要同時有 10 張以上未結 PO，第一個月幾乎必定抓到至少一張逾期未確認。）

## 6. 執行方式

```bash
# 離線驗收：零憑證、零網路
PYTHONUTF8=1 python main.py --mock

# 只看報告不送出、不寫狀態檔
PYTHONUTF8=1 python main.py --mock --dry-run

# 指定狀態檔（多客戶共用同一份程式碼時，每個客戶一個狀態檔）
PYTHONUTF8=1 python main.py --mock --state-file ./state/client-acme.json

# 真實模式（需要 ERP token + 信箱憑證 + Anthropic API Key）
PYTHONUTF8=1 python main.py --live --notify telegram
```

排程（每個工作日早上 08:30 跑一次）：

```cron
30 8 * * 1-5  cd /path/to/demo20-vendor-tracking && python main.py --live --notify telegram
```

退出碼：`0` = 全部在期程內且回覆全數解析成功；`2` = 有逾期或有解析失敗（需人工處理）；`1` = 致命錯誤。

## 8. 設計決策（為什麼這樣寫）

### 1. 一張 PO 只發最嚴重的那一則警報

`PO-20260812` 同時符合「逾期未到貨」與「交期將至但尚未出貨」兩條規則。
報告只印前者。採購人員早上看到 20 行警報時，第 15 行寫什麼已經不重要了；
四條規則依嚴重度排序，第一個命中就停。

### 2. 準時率對照「原始承諾交期」，逾期偵測對照「最新承諾交期」

兩個日期刻意用在不同地方：

- **催辦**看的是供應商最新給的日期（`revised_eta`）——你要催的是他現在承諾的那天。
- **計分卡**看的是最初的承諾（`order.eta`）——否則供應商只要不斷改期就能維持 100% 準時率，
  計分卡就失去談判籌碼的意義。

### 3. 沒有母體的比率一律印「—」，不印 0%

`Kaohsiung Precision Works` 本期沒有任何一張到貨，準時率是 `None` 而不是 `0.0`。
「這個月沒有到貨」與「這個月每一張都遲到」是完全不同的事，
把兩者混為一談會讓整張計分卡在談判桌上失去可信度。提示詞裡也把這條寫成強制規則。

### 4. 狀態完全由郵件推導，ERP 只提供「有哪些 PO」

`mock/purchase_orders.json` 裡沒有 `status` 欄位。這讓整個流程冪等：
同一批郵件跑幾次都得到同一組狀態，不會因為狀態檔壞掉就永久失真。
狀態檔只存**催辦冷卻紀錄**與已處理的郵件 ID。

### 5. 催辦信一次全部產生，再依 PO 拆回去

LLM 只呼叫一次，用 `--- PO-XXXX ---` 分隔線切段。
如果某張 PO 沒有出現在回應裡，會**退回制式範本並發 AMBER**——
寧可寄出一封制式的信，也不能讓一張逾期的 PO 無聲地沒被催。

### 6. 時區用標準庫 `zoneinfo`，載不到就退固定偏移並警報

Windows 沒有系統 tz database，裸環境的 `ZoneInfo("Asia/Taipei")` 會直接失敗。
本模組退回 `utc_offset_hours` 指定的固定偏移並發 AMBER，
**刻意不退回機器本地時間**：同一批資料在不同機器算出不同的逾期時數，比「時區載不到」更難查。
（不使用 `pytz`——那是標準庫尚未提供 `zoneinfo` 年代的替代品。）

### 7. 檔名是 `supplier_mail.py` 而不是 `mailbox.py`

`mailbox` 是 Python 標準庫模組名。demo 目錄會被插到 `sys.path` 最前面，
取名 `mailbox.py` 會遮蔽標準庫，將來任何相依套件 `import mailbox` 都會拿到這一份。

## 10. 已知限制

| 限制 | 說明 |
| --- | --- |
| 分類靠關鍵字 | 供應商用全新措辭（例如只回「OK」）會落入 `unclassified` — 但**會警報**，不會被當成沒事 |
| 只讀 text/plain | 純 HTML 信件取不到內文，會因分類失敗而警報 |
| 不解析附件 | PDF 出貨單／發票不會被讀取，只認信件本文 |
| 一封信只綁一張 PO | 一封信提到多張 PO 會判為 `ambiguous_po_number` 並警報，不猜 |
| 不比對數量差異 | 書中的「到貨時自動比對差異」目前只比對**時間**，數量／品項差異需 ERP 收貨單支援 |
| ERP 為唯讀 | 本 demo 只讀未結 PO，不回寫 ERP 狀態（回寫是不可逆動作，需另設自主權閘門） |

前四項全都會**明確警報**而不是靜默失敗——這是本模組與「看起來每天都在跑」的假監控最大的差別。
