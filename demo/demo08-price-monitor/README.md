# demo08 — 競品價格監控警報

> 《The OpenClaw Income Engine》第 03 章 · 模組 #8 · 業務增長階段
> 部署 **<60 分鐘**｜回收 **11 hrs/mo（$770）**｜售價 **$280 setup + $70/mo**

每天 07:00，Agent 抓一輪競品頁面價格、和昨天的基準比對，
變動幅度達到閾值就在你喝第一口咖啡之前告訴你。

## 核心流程

```
07:00  排程器觸發
  ↓
抓取   逐一取得競品頁面（間隔 >=1 秒，避免被封 IP）
  ↓
解析   用標準庫 html.parser 依 selector 取出價格字串 → Decimal
  ↓        ├─ 解析成功 → 進入比對
  ↓        └─ 解析失敗 → **AMBER 警示**（絕不靜默跳過）
比對   與狀態檔中的基準價比對，算出變動百分比
  ↓
判定   |變動| >= threshold_percent → 列入警報
  ↓
摘要   Claude 依 prompts/alert_summary.md 寫成 220 字內的人話警報
  ↓
發送   依自主權層級決定「自動送出」或「留為草稿待核准」
  ↓
落帳   把本次價格寫回狀態檔，成為明天的基準
```

### 退出碼

| 碼 | 意義 |
| --- | --- |
| `0` | 全部目標解析成功 |
| `2` | 流程完成，但**有目標解析失敗**（AMBER，需人工確認 selector） |

排程器請把 `2` 當成「有事要看」而不是「壞掉」——這正是本模組刻意分開兩種訊號的原因。

## 設定（`config.yaml`）

| 欄位 | 說明 |
| --- | --- |
| `monitor.run_at` | 晨間執行時間，預設 `"07:00"`（實際排程交給 cron，本欄用於報告標頭） |
| `monitor.threshold_percent` | 警報閾值，預設 `5`。判定用 `>=`，剛好 5.00% 也會警報 |
| `monitor.request_interval_seconds` | 抓取間隔，預設 `1`。實際取 `max(本值, 1.0)` |
| `monitor.state_file` | 基準價狀態檔，預設 `state/baselines.json` |
| `targets[].selector` | 支援 `tag` / `.class` / `#id` / `[attr=value]` 及其組合 |
| `targets[].baseline_price` | **字串**格式（`"129.00"`），避免 YAML 轉 float 掉精度 |

基準價的優先序是 **狀態檔 > config**：`baseline_price` 只是第一次執行的種子值，
之後每天都以「昨天實際觀測到的價格」為基準滾動。

## 設計決策（為什麼這樣寫）

### 1. 解析失敗必須警報，不可靜默跳過

這是本模組最重要的一條規則。**網站改版讓 selector 失效，是價格監控最常見的無聲故障**：
監控器看起來每天都在跑、每天都回報「無異常」，但它其實早就什麼都沒看到。
等你發現時，已經瞎了三個月。

因此：

- 任何解析不出價格的目標，都帶著 `failure_reason` 回傳，走 `Diagnostics.amber`
- 報告標頭必定寫出「**N 個目標解析失敗**」
- 失敗的目標**不會**被寫進狀態檔（否則明天會拿錯誤的基準去比對）
- 失敗的目標**不會**被當成「價格無變動」混進比對結果

`mock/pages/competitor_e.html`（改版失效）與 `competitor_f.html`（價格欄位變成
`Call for pricing`）就是專門用來釘住這個行為的兩份快照。

### 2. 抓取間隔 >= 1 秒

競品站台不歡迎爬蟲。低於 1 req/s 很容易被判定為攻擊而封 IP，
那會讓監控器連續幾天靜默失效——正好是第 1 點要防的那種災難。
mock 模式讀本地檔案、完全不觸網，所以不套用節流。

### 3. 金額一律 `decimal.Decimal`

價格差異是要拿去談判與定價的數字。用 float 會出現
`0.1 + 0.2 != 0.3` 這種在客戶面前無法辯解的誤差。
從 YAML 讀進來的 float 也會先經 `str()` 再進 `Decimal`，避免把二進位誤差帶進來。

### 4. 只用標準庫 `html.parser`

交付給客戶的單檔部署包，不該為了抓一個價格而背上 BeautifulSoup / lxml 依賴
（lxml 在 Windows 上還常常裝不起來）。代價是只支援 CSS 選擇器的一個子集，
但對「抓某個元素的價格」這件事已經夠用。

### 5. 預設 `draft` 自主權

價格警報如果誤判就直接推到團隊或客戶頻道，殺傷力不小。
預設維持 `draft`：警報只印在本機等人工過目。
要開 `supervised_auto` 必須填 `approved_senders` 白名單，
且書中鐵律要求先在草稿模式跑滿 14 天——未滿會留下 AMBER 警告。

## Client Pitch

> **「永遠不成為最後一個知道市場變化的人。」**

**開場**：你上次知道競爭對手降價，是自己看到的，還是客戶告訴你的？

**痛點**：多數老闆的答案是後者。那代表在你知道之前，
你的報價已經在某個比價頁上輸了好幾天——而且輸得無聲無息。

**方案**：$280 建置、$70/月。每天早上 07:00，
你會在打開電腦之前就知道昨天誰動了價格、動了多少、要不要跟。

**風險反轉**：第一個月照跑，如果一次有效警報都沒有，退費。
（實務上不會發生——只要監控 5 個以上競品，第一個月幾乎必定抓到至少一次調價。）

## 已知限制

| 限制 | 說明 |
| --- | --- |
| 選擇器只支援子集 | `tag` / `.class` / `#id` / `[attr=value]`，不支援後代、`:nth-child` 等組合器 |
| 只取第一個命中元素 | 頁面有多個同 selector 的價格時，取文件順序第一個 |
| 小數點固定為 `.` | 歐陸「1.299,00」逗號小數格式會解析錯誤，需另外處理 |
| 不執行 JavaScript | 價格由前端 JS 渲染的站台抓不到，會回報為「找不到對應元素」並警報 |
| 不處理反爬蟲 | 遇到 Cloudflare 挑戰頁會解析失敗並警報，需人工改走其他資料來源 |

最後三項全都會**明確警報**而不是靜默失敗——這正是本模組的設計重點。
