# 模組 #12 — 潛在客戶生成管線（Lead Generation Pipeline）

> **This is not a pipeline problem. This is a qualification problem.**
> 部署 **1 Day**｜每週回收 **20+ 小時**｜內部價值 **$5,200/mo**（管線容量 3-4×）
> 售價 **$900 首付 + $220/月**（附錄 F 定價；第 05 章另有一組較高定價，見第七節）

來源：《The OpenClaw Income Engine》第 05 章 p05（潛在客戶生成管線）+ 附錄 F p06（潛在客戶開發管線）。
兩處的模組名稱略有出入（「生成」vs「開發」），本模組採第 05 章名稱。

## 一、原著診斷：問題不在管線，在資格審查

> 「銷售團隊花了 **40%** 的時間在研究永遠不會購買的潛在客戶。
> 這不是管線問題，這是『資格審查』問題。」 — ch05_p05

```
        ┌──────────────────────┐
        │   看起來很滿的管線    │   ← 名單一直加，會議卻沒變多
        └───────────┬──────────┘
                    │
        ╔═══════════▼══════════╗
        ║  主觀感受式的資格審查 ║   ← 真正的瓶頸
        ║  「feels like a fit」 ║      沒有標準 → 無法複製 → 無法交接
        ╚═══════════┬══════════╝
                    │  40% 的業務時間消耗在這裡
        ┌───────────▼──────────┐
        │    真正該談的那幾家    │
        └──────────────────────┘
```

**關鍵洞察**：資格審查不是「花時間就會準」的工作，而是「有沒有一致標準」的工作。
人工審查的問題不在慢，在**每個人的標準不一樣、而且沒有一次是可稽核的**。
本模組把「感覺對不對」換成 **0-100 分的可解釋分數**——每一分都附得出證據。

## 三、ICP 評分引擎

原著 ch05_p05 要求設定 `ICP_CRITERIA`（產業、規模、技術特徵）；
apxF_p06 要求 `ICP Scoring Engine` 依權重計算 0-100 分（產業匹配度、公司規模、觸發事件）。
兩者聯集即下列四個面向：

| 面向 | 權重 | 滿分條件 | 半分條件 | 零分條件 |
| --- | :---: | --- | --- | --- |
| 產業匹配 | **35** | 命中 `target_industries` | 命中 `adjacent_industries` | 其餘 |
| 公司規模 | **25** | 落在理想區間 50-500 人 | 落在可接受區間 20-1500 人 | 區間外 / 未提供 |
| 觸發事件 | **25** | 已知事件型別且在 45 天內 | 有事件但缺發生時間 | 無事件 / 已過期 / 未知型別 |
| 技術特徵 | **15** | 命中 2 項以上偏好技術 | 命中 1 項 | 未命中 / 未提供 |

- 權重總和必須是 100。不是 100 時程式**等比正規化並發出 AMBER 警告**，
  而不是靜默照算——分數會被拿去對客戶解釋，來源必須說得清楚。
- 分數帶：**Hot 75-100 / Warm 50-74 / Cold 0-49**。
  ⚠️ 原著 #12 只寫「評分 1-100」與「Hot Leads 推送至 CRM」，**未給門檻數字**；
  此處沿用同書 #16（ch05_p09）的 `SCORE_THRESHOLDS`，並在 `config.yaml` 註明出處。
- 分數表示法：原著兩處分別寫 **1-100**（ch05）與 **0-100**（apxF）。本實作採 **0-100**
  （零分必須是可表達的狀態，否則「四項全不命中」無法被正確表示）。

### 觸發事件的時效性

超過 `trigger_recency_days`（預設 45 天）的事件一律計 0 分。
理由：破冰話題的價值來自時效。引用兩個月前的募資新聞，
傳達的訊息不是「我做了功課」，而是「我用的名單很舊」。

### 為什麼「評分」與「能不能寄」是兩件事

| | 評分（`LeadScorer`） | 發送權限（`ComplianceGate`） |
| --- | --- | --- |
| 對外部的影響 | 無（純內部分析，READ_ONLY 安全） | 有（實際寄信給陌生人） |
| 適用對象 | **所有**線索，包含不能聯繫的 | 只有通過四道法遵閘門的 |
| 失敗代價 | 排序不準，人工可修正 | 觸法 / 網域信譽受損，**不可逆** |

mock 資料裡的 `L-2005` 就是這個設計的證明：**90 分的 Hot Lead，但命中抑制名單，
一封都不會寄**。分數照樣算出來給業務看（他可以決定要不要改用電話或轉介），
但外送這條路是關死的。

### 資料不完整的線索：不寄，也不丟

必要欄位完整度低於 `min_completeness`（預設 0.6）時，線索進入**補資料佇列**。

- 不寄的理由：拿殘缺資料做「個人化」，寫出來的是「貴公司近期的發展」這種空話，
  比不寄更傷——它明確告訴對方「這是群發」。
- 不丟的理由：低完整度算出的低分是「**我們不知道**」，不是「這家公司不適合」。
  把它當成 Cold Lead 丟掉，等於用資料收集的失誤懲罰潛在客戶。

## 四、三階段外聯節奏

| 段 | 天數 | 型別 | 目的 | 字數上限 | 提示詞 |
| --- | --- | --- | --- | :---: | --- |
| 1 | Day 0 | `icebreaker` | 用觸發事件證明「我真的看過你們公司」 | **150** | `prompts/stage1_icebreaker.md` |
| 2 | Day 4 | `value_proof` | 帶新東西進來：可驗證的做法（機制，不是戰績） | 180 | `prompts/stage2_value_proof.md` |
| 3 | Day 9 | `breakup` | 體面收尾，把選擇權交還對方 | 120 | `prompts/stage3_breakup.md` |

- **150 字**取自 apxF_p06 原文；**Day 0 / 4 / 9 的天數是實作補充**，原著只寫「3 階段跟進」。
- 到期日 = `discovered_at + N 天`，**不用絕對日期**，序列可隨時重新排程而不錯亂。
- 三段送完即停，不循環、不自動重啟。要再接觸必須由人重新放入管線。
- 提示詞硬性規定**不得編造客戶案例與成效數字**——本專案的原始素材沒有任何客戶見證
  可引用（見第八節），模型若自行生成一個公司名，那就是偽造。

### 自主權階梯

| 層級 | 行為 |
| --- | --- |
| `read_only` | 只評分與排序，不產生任何信件 |
| `draft`（**預設**） | 全部產出草稿，人工審核後送出 |
| `supervised_auto` | 僅自動送給 `approved_senders` 白名單；未命中一律降級為 `draft` |

書中鐵律：**未在 DRAFT 模式運行滿 14 天、且未取得客戶簽核前，不得開啟全自動**。
未滿 14 天就設 `supervised_auto` 會收到 AMBER 警告。

本模組另加一條：**寄件人識別（第六節）不齊備時，即使命中白名單也一律降級為草稿**。
理由見下一節——沒有合法識別的信不該被寄出去，白名單管的是「寄給誰」，
不是「這封信合不合法」。

## 五、法遵閘門的兩道關卡

```
每日排程判定                        實際發送前
────────────                        ──────────
ComplianceGate.check()              OutreachPlanner.assert_can_send()
  → 缺 email？                        → 再查一次抑制名單與來源合法性
  → 命中抑制名單？
  → 來源依據合法？
  → 屬 opt-in 法域且無同意紀錄？
                    ↓ 中間隔著 LLM 生成時間（數十秒到數十分鐘）
                      對方完全可能在這段空窗按下退訂
```

只在排程時查一次是不夠的。本模組在每一封信實際送出前都會再查一次
（`OutreachPlanner.assert_can_send`），正式環境可把抑制名單換成即時查詢，
而不是沿用排程當下的快照。

## 六、⚠️ 冷開發信的法遵風險（實作補充，非原著內容）

> **本節不是原著內容。** 34 張投影片完全沒有提到冷開發信的法律風險。
> 這一節是**主 Claude 要求補充**的實務必要條件——一個「主動對外發送」的模組
> 若不處理這一層，交付出去就是把法律風險轉嫁給客戶。
> 以下敘述屬實作補充，不可視為原著主張，亦**不構成法律意見**；
> 實際部署前請由客戶的法務確認。

### 6.1 三套法規的最低要求

| 法規 | 適用 | 本模組的對應實作 |
| --- | --- | --- |
| **GDPR**（歐盟） | 對歐盟境內個人的行銷 | `consent_required_regions` 清單命中且無 `has_opt_in` 紀錄 → 直接阻擋；footer 依第 14 條告知**資料來源** |
| **CAN-SPAM**（美國） | 商業電子郵件 | footer 強制含**可辨識寄件人 + 實體郵寄地址 + 有效退訂管道**；不得使用誤導性主旨 |
| **個人資料保護法**（台灣） | 個資的蒐集/處理/利用 | `allowed_source_bases` 限定合法蒐集來源；退訂即納入抑制名單，永久不再聯繫 |

### 6.2 四道閘門（`ComplianceGate`）

| 閘門 | 判定 | 阻擋原因鍵 |
| --- | --- | --- |
| 聯絡管道 | 沒有 email 就沒有退訂管道，不得寄 | `missing_email` |
| 抑制名單 | 命中即**永久**不得再聯繫（退訂 / 要求刪除 / 客訴） | `suppressed` |
| 來源合法性 | `source_basis` 必須在白名單內 | `unlawful_source` |
| 同意法域 | opt-in 法域（DE/AT/FR/NL…）無同意紀錄不寄 | `consent_required_region` |

**`purchased_list`（購買名單）刻意不在合法來源清單內。**
在 GDPR 下，透過名單商取得的個資幾乎不可能主張「合法利益」，
而且對方根本不知道資料是怎麼到你手上的。mock 資料的 `L-2006` 就是這個情況：
**100 分滿分，照樣擋下**。

### 6.3 兩條設計上的硬規則

1. **`require_unsubscribe` 設定檔改不掉**。
   `config.yaml` 即使寫 `false`，`ComplianceGate` 建構子也會強制覆寫為 `True`，
   透過 `Diagnostics.amber()` 發出警示並寫進執行結果的 `warnings`。
   理由：一封沒有退訂管道的冷開發信，換來的是對方按下「檢舉垃圾郵件」，
   受損的是**整個寄件網域的信譽**，不只是這一封——這種傷害不可逆，
   不能交給設定檔決定。

2. **退訂與識別區塊由程式串接，不交給 LLM 生成**。
   `ComplianceGate.footer()` 在 LLM 輸出之後才附加，三個提示詞都明文禁止模型
   自行撰寫署名、地址或退訂連結。理由：法定必要資訊不能依賴模型「記得寫」，
   也不能讓模型有機會改寫退訂連結或郵寄地址。

3. **寄件人識別不齊備 → 全部降級草稿**。
   `sender_identity` 五個欄位（寄件人、公司、實體地址、回覆信箱、退訂連結）
   任一空白或仍是未展開的 `${ENV}`，本次執行一律不自動外送。

### 6.4 交付前的法遵檢查清單

```
- [ ] 抑制名單已從客戶既有系統匯入（不是空的）
- [ ] sender_identity 五個欄位填的是客戶的真實資訊
- [ ] 退訂連結實際可用，且退訂後會寫回抑制名單
- [ ] allowed_source_bases 經客戶法務確認
- [ ] 目標名單中的歐盟聯絡人已確認有同意紀錄，否則移除
- [ ] 客戶已被明確告知：本模組不提供法律意見
```

## 九、Client Pitch（銷售話術）

**原文（apxF_p06，逐字引述；原投影片此處有裁切，省略號為原文所有）**：

> 「Your pipeline fills automatically — every lead researched, scored... before your

**繁體中文翻譯**：

> 「您的管線會自動填滿——每一個潛在客戶都已經被研究過、評過分……
> 而這一切都發生在您的業務團隊打開筆電之前。**他們負責成交，代理人負責資格審查。**」

**話術補充（現場對答用）**

| 客戶疑慮 | 回應 |
| --- | --- |
| 「評分準嗎？」 | 每一分都附得出證據——哪個產業、幾人、什麼事件、幾天前、命中哪些技術。您可以逐條反駁，然後我們改權重。這比「我覺得這家不錯」可稽核得多。 |
| 「會不會被當成垃圾信？」 | 這是我們優先權最高的設計。四道法遵閘門會先擋掉不該寄的：買來的名單、退訂過的人、歐盟未取得同意的聯絡人。退訂連結與寄件人資訊由系統附加，不經 AI 生成。 |
| 「我的業務自己找不行嗎？」 | 可以，而且他們本來就在做——只是花掉 40% 的時間在不會買的人身上。差別不是能力，是有沒有一致的標準。 |
| 「資料不完整的怎麼辦？」 | 不寄，也不丟。進補資料佇列。用殘缺資料做出來的「個人化」，對方一眼就看得出是群發，那比不寄更傷。 |
| 「$220 會不會太貴？」 | 以每週回收 20 小時、工時 $65 計算，每月價值 $5,200。月費是它的 4%。 |

## 十、使用方式

## 十二、已知限制

- **本 demo 不含 CRM 寫回。** 結果會標記 `crm_push`（Hot Lead 應推送至
  `crm.hot_lead_destination`），但實際的 HubSpot / Salesforce API 呼叫未實作。
  正式部署需在 `_process_outreach` 之後補上，否則下次執行只能依賴本機狀態檔。
- **不含 Apollo.io 資料豐富化。** 原著要求串接 Apollo API 補齊公司資料；
  本 demo 的補資料佇列只到「標記出缺哪些欄位」為止，實際補值需另接。
  第三方依賴限制（只允許 PyYAML / pytest）也讓本 demo 無法示範真實 API 呼叫。
- **抑制名單是靜態快照。** 正式環境務必改成即時查詢，
  否則「排程判定與實際送出之間對方剛退訂」這個空窗仍會漏。
- **法遵判定是規則式的，不是法律意見。** `consent_required_regions` 只是一份清單，
  無法涵蓋各國法規的細節與例外。交付前必須由客戶法務確認（見第 6.4 節）。
- **提示詞只有單一語言版本。** 對歐美客戶做冷開發需要英文版提示詞；
  多語系需為每個語言複製一組 `prompts/`。
- **分數門檻沿用 #16 的定義**（Hot 75 / Warm 50）。原著 #12 未給門檻，
  若客戶的 ICP 分布明顯不同，應以其歷史成交資料重新校準，而非沿用預設值。
