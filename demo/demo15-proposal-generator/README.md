> 敘事由 LLM 撰寫、**價格由程式依 RATE_CARD 計算**、電子簽署**永遠等人按下送出**。

## 1. Before / After

| 階段 | Before（人工） | After（Agent） |
| --- | --- | --- |
| 取得客戶脈絡 | 翻 CRM、翻 Email、回想會議說了什麼 | 讀 CRM Deals + Meeting Notes + Company Profile（**The Eyes**） |
| 研究客戶背景 | 手動 Google 客戶公司近況 | 公司背景與近期新聞隨交易一併帶入提示詞 |
| 寫敘事 | 拿上一份提案狂改，常留著前一個客戶的名字 | LLM 依會議筆記重寫四個段落（**The Brain**） |
| 組報價 | 手動拼 Excel，單價靠記憶，偶爾漏一項 | `RATE_CARD` 計算 A/B/C 三個投資選項（**Decimal，全程禁 float**） |
| 折扣 | 業務當場口頭給，事後才發現吃掉毛利 | 級距表自動套用，超過上限**夾到上限並轉人工核價** |
| 排版與交付 | 複製到 Word 調格式 | 產出格式一致的提案文件（**The Hands**） |
| 送簽 | 手動建 DocuSign 信封 | 產出**待人工核准**的簽署請求單，**永不自動送出** |
| 耗時 | 資深人員 **2–4 小時／份** | 生成 **< 2 分鐘**，人工只需覆核與核准 |

### 架構：The Eyes / The Brain / The Hands

```
[The Eyes]                   [The Brain]                         [The Hands]
CRM Deals            ──►  OpenClaw + Claude               ──►  提案文件（Markdown/PDF）
Meeting Notes             ├─ pricing.py：RATE_CARD 計算         ├─ 狀態：草稿・待核准
Company Profile           │   A / B / C 三個投資選項            ├─ 寫入提案台帳（--state-file）
                          │   折扣級距 → 稅 → 首年總額           └─ DocuSign 簽署請求單
                          │   （全程 Decimal，禁 float）             status = pending_human_approval
                          ├─ LLM 撰寫敘事（**不得產生金額**）         is_sent = False  🔒
                          ├─ 金額遮蔽器：模型寫的數字一律遮掉
                          └─ 超出範圍 ──► needs_pricing_review
                                          （轉人工核價）
```

## 2. 🔒 安全鐵律：電子簽署需人工核准

SPEC #15 的 Output 段原文寫的是「自動化發送電子簽署流程（**依核准模式**）」。
本模組把「依核准模式」實作成**程式層的硬阻斷**，而不是一句設定或一行註解。

### 為什麼這條不能妥協

**提案是草稿，簽名是締約。** 生成一份寫錯的提案，最壞的結果是業務退回重寫；
但把簽署請求送到客戶信箱，客戶只要按一下就完成簽署——那一刻文件成立為合約，
公司必須依上面的金額履約。差別不在於錯誤的機率，而在於**錯誤是否還救得回來**：

- 報價算錯 → 人工覆核時攔得下來。
- 客戶已簽 → 只能談和解或吃下虧損。

AI 可以草擬合約，但**不得代替公司締約**。締約是法律行為，必須由有權限的人做出決定。

### 這條鐵律怎麼被程式保證

| 防線 | 實作位置 | 行為 |
| --- | --- | --- |
| 沒有送出的能力 | `proposal_builder.build_signature_request()` | 函式**不接受任何 `send=True` 參數**；能被參數打開的鐵律不是鐵律 |
| 狀態恆定 | 同上 | `status` 恆為 `pending_human_approval`、`is_sent` 恆為 `False` |
| 設定檔關不掉 | `main._resolve_signature_config()` | `signature.require_human_approval` 被改成 `false` 時，程式**強制改回 `true`** 並發 AMBER |
| 自主權無法繞過 | `test_main.py::test_integration_...` | 即使 `--autonomy supervised_auto`，`signatures_sent` 仍斷言為 `0` |
| 文件上寫明 | `_render_footer()` | 每份提案結尾都印出簽署狀態與阻斷理由 |
| 零網路呼叫 | 全模組 | 本模組沒有任何 DocuSign 送出用的 HTTP 呼叫程式碼 |

人要送簽，必須自己登入 DocuSign 後台按下送出——這是刻意的摩擦，不是尚未實作的功能。

### 第二條鐵律：價格不由 LLM 產生

| 防線 | 行為 |
| --- | --- |
| 提示詞 | `prompts/draft_proposal.md` 以「最高優先規則」明令：不得出現任何幣別符號、金額、折扣百分比，不得推算或換算價格 |
| 事後遮蔽 | `redact_monetary_tokens()` 掃描敘事，任何金額樣式一律遮成 `［金額由系統計算後填入］` 並發 AMBER |
| 不回填文件 | 被遮蔽的原始字串**不印回提案文件**，只留在執行結果與診斷訊息中供內部覆核 |
| 精度 | 金額全程 `decimal.Decimal`；`to_decimal()` **直接拒收 float**，設定檔漏加引號會當場報錯 |

> 實測動機：模型很擅長從會議筆記的預算暗示外推一個「看起來很合理」的價格。
> `mock/narratives/HRG-2026-088.md` 就刻意保留了兩處這種數字（`$4,500`、`US$350`），
> 用來證明遮蔽機制真的會攔下來。

## 3. 報價規則（config.yaml）

### RATE_CARD（定價卡）

| 代碼 | 服務項目 | 計費 | 單價 | 數量上限 |
| --- | --- | --- | ---: | ---: |
| `discovery_workshop` | 探索工作坊 | 一次性 | $1,200 / 場 | 4 |
| `automation_module` | 自動化模組建置 | 一次性 | $1,000 / 個 | 10 |
| `crm_integration` | CRM 系統整合 | 一次性 | $1,800 / 式 | 3 |
| `data_migration` | 歷史資料遷移 | 一次性 | $2,500 / 式 | 2 |
| `training_session` | 團隊教育訓練 | 一次性 | $600 / 場 | 6 |
| `retainer_standard` | 標準維運訂閱 | 每月 | $200 / 月 | 12 |
| `retainer_priority` | 優先支援訂閱 | 每月 | $450 / 月 | 12 |
| `analytics_dashboard` | 成效儀表板訂閱 | 每月 | $250 / 月 | 12 |

### A / B / C 三個投資選項（SPEC #15 的 `Pricing Strategy`）

| 方案 | 內容 | 定位 |
| --- | --- | --- |
| A — 基礎版（Essential） | 客戶指定的核心服務 | 只做最痛的那一段，最快看到結果 |
| B — 推薦版（Recommended）★ | A ＋ 教育訓練 ＋ 標準維運訂閱 | 交付後客戶能自行運作 |
| C — 完整版（Comprehensive） | B ＋ 歷史資料遷移 ＋ 成效儀表板 | 一次到位 |

各方案的 `add_ons` 在 `config.yaml` 中**完整列出**而非繼承上一階——避免日後改動時發生隱性疊加。

### 折扣 / 稅 / 有效期限

| 規則 | 值 | 說明 |
| --- | --- | --- |
| 折扣級距 | 小計 ≥ $20,000 → 15%；≥ $10,000 → 10%；≥ $5,000 → 5% | 由大到小比對，第一個命中勝出 |
| 折扣基準 | 只作用於**一次性費用** | 月費打折會直接侵蝕 MRR 的健康度 |
| 業務手動折扣 | 取級距與手動值的**較大者** | 超過上限則夾到上限並轉人工核價 |
| 折扣上限 | 20% | `pricing.guardrails.max_discount_rate` |
| 稅率 | 5% | `pricing.tax_rate` |
| 報價有效期限 | 14 天 | 文件標頭與台帳都會記錄到期日 |
| 自動報價天花板 | 含稅建置費 $25,000 | 超過即轉人工核價 |

> ⚠️ **原簡報只提供了「RATE_CARD」與「A/B/C 三選項」兩條規則**，
> **沒有**提供稅率、折扣級距、有效天數與天花板。上表後四項是本模組的**部署預設值**，
> 交付客戶前必須依當地稅制與該公司的商務政策改寫。這一點在 `config.yaml` 內也標註了。

### 超出自動報價範圍的三種情況

命中任一項即把提案標為 `needs_pricing_review`，交業務主管人工核價：

1. **折扣超過上限**——夾到上限，不照給、也不靜默忽略。
2. **數量超過 RATE_CARD 上限**——代表交付量能需要人工確認（例：教育訓練 7 場 > 上限 6 場）。
3. **含稅建置費超過天花板**——這種規模的案子不該由自動化決定價格。

`mock/deals.json` 的第三筆（Meridian Global Holdings）刻意同時觸發這三種情況。

## 6. Client Pitch 話術

原簡報的 Client Pitch 有英文原文（ch05_p08），照錄如下：

> **原文**：
> 「A first-draft proposal in your client's inbox within two hours of the discovery call...
> You review. You approve. You win more.」
>
> **繁中翻譯**：
> 「探索會議結束後兩小時內，一份提案初稿就會出現在您客戶的信箱裡……
> 您負責審閱。您負責核准。您贏得更多案子。」

注意這句話的結構：三個動詞的主詞**全都是「您」**——審閱是人、核准是人、贏也是人。
自動化只負責「兩小時內生出初稿」這一段。本模組的實作嚴格照這個分工，沒有多做一步。

補充三句（客戶一定會問的）：

1. **「它會不會亂報價？」**——價格完全不由 AI 產生。所有金額由定價卡計算，
   AI 寫出來的任何數字都會被系統遮蔽並警示。超出折扣上限或報價天花板的案子，
   它會直接停下來要求人工核價。
2. **「它會不會把提案直接寄給我的客戶？」**——預設不會。預設模式是產出草稿等您核准；
   要開啟自動寄送，必須明確把該客戶的網域加進白名單。
   而**電子簽署永遠不會自動送出**，這一項無論怎麼設定都關不掉。
3. **「寫出來的東西會不會很罐頭？」**——敘事的每一點都必須能在探索會議筆記中找到出處，
   提示詞明令不得擴充會議沒談過的事。它不是在套模板，是在重述您跟客戶談過的內容。

## 7. 使用方式

```bash
# 標準離線驗收（零憑證、零網路）
python main.py --mock

# 跑完流程但不寫檔、不寫台帳、不通知
python main.py --mock --dry-run

# 固定報價日，讓有效期限可重現
python main.py --mock --as-of 2026-08-24

# 白名單客戶可自動寄出提案草稿（電子簽署仍然不會送出）
python main.py --mock --autonomy supervised_auto

# 指定台帳與輸出位置
python main.py --mock --state-file ~/openclaw/proposals.json --output-dir ~/openclaw/proposals

# 串接真實 Claude + CRM 匯出檔（需環境變數）
python main.py --live --notify telegram
```

`--live` 所需環境變數（一律不寫進設定檔）：

| 變數 | 用途 |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID_CHENGHYANG2001BOT` | Telegram 通知 |

Claude 撰寫提案敘事走本機 `claude` CLI／Max 訂閱 OAuth，不需要 `ANTHROPIC_API_KEY`。

`--live` 另需在 `config.yaml` 填入 `crm.export_path`（CRM 匯出的 JSON，含 Deals / Meeting Notes /
Company Profile）。未填會直接觸發紅色警報停下來，不會靜默跑成空結果。

## 9. 已知不一致與限制

### 9a. 定價：第 05 章與附錄 F 不一致（原著問題）

| 來源 | 建置費 | 月費 | 本模組處理 |
| --- | ---: | ---: | --- |
| **附錄 F（apxF_p09）** | **$1,000** | **$200/月** | ✅ **採用**（`module.client_setup_price` / `client_monthly_price`） |
| 第 05 章（ch05_p08） | $950 | $260/月 | 列為 premium tier，僅記錄於 `module.premium_*`，不參與任何計算 |

**premium tier 的定位**：第 05 章那組是「較低首付、較高月費」的組合（首付 −$50、月費 +$60），
第 8 個月起累計金額就會超過附錄 F 那組。若客戶偏好壓低前期投入，可改用這組報價，
但必須知道這是**原著兩處不一致的其中一個版本，不是本模組驗算過的第二方案**。

原簡報的定價不一致遍及 #11–#17（僅 #18/#19/#20 兩來源一致），詳見 `SPEC-11-20.md` 差異 1。

### 9b. 其他限制

- **不產生 PDF**：輸出為 Markdown，PDF 排版交由下游工具處理（避免為了一個轉檔功能引入額外依賴）。
- **不上傳 Google Drive、不寄 Email 給客戶**：`delivery_mode` 只標記「該不該自動送」，
  實際外送由既有的 Notifier 通道或人工處理。
- **不呼叫 DocuSign**：見 §2，這是設計，不是待辦。
- **不做多幣別換算**：整份報價使用 `pricing.currency` 單一幣別。
- **稅率為單一比例**：不支援分項稅率或跨境稅務規則；跨國客戶必須人工核價。
- **敘事品質仰賴會議筆記**：筆記寫得含糊，提案就只會寫出含糊的「我們的理解」——
  這是刻意的，模型被明令不得補充會議沒談過的事實。
