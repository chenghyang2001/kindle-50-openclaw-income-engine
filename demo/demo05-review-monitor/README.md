# demo05 — 客戶評價監控與回覆草擬

> 模組 #5｜階段：品牌與聲量｜部署 < 60 分鐘｜回收 11 hrs/mo｜售價 **$300 setup + $80/mo**

每 6 小時掃一次 Google / Trustpilot / Amazon，偵測新評價、評分情緒、依品牌語氣草擬回覆，
並依星等走**兩條完全不同的通知路徑**：1–2 星負評在 30 分鐘內單獨推播到手機，
3–5 星評價併成一則彙整。平均回應時間從 **3.2 天壓到 4 小時內**。

## Before / After

| | Before（人工） | After（代理程式） |
| --- | --- | --- |
| 監控方式 | 想到才手動開 Google、Trustpilot、Amazon 各看一遍 | 每 6 小時自動輪詢全部平台 |
| 漏看風險 | 忙起來整週沒看；負評閒置 48 小時造成嚴重聲譽損害 | 新評價一出現就進入處理佇列，去重機制確保不重複也不遺漏 |
| **平均回應時間** | **3.2 天** | **4 小時內** |
| 負評處理 | 和好評混在一起，等有空才一起看 | **升級路徑**：1–2 星立即單獨推播，**30 分鐘內**到手機，不等彙整批次 |
| 回覆撰寫 | 每則從零開始想措辭，情緒上頭時容易寫壞 | 依品牌語氣檔草擬，附情緒判讀與建議下一步 |
| 語氣一致性 | 看當天心情，五星回覆常變成同一句罐頭 | 品牌語氣檔 + 3–5 則真實樣本校準，星等不同結構不同 |
| 每月耗時 | 約 11 小時（含來回查找、寫、貼） | 約 1.5 小時（純審查與送出） |

## 雙軌通知路徑（本模組的核心設計）

```
每 6 小時輪詢
      │
      ├─ 抓取（live 模式每平台間隔 >= 1 秒，rate limit 防護）
      ├─ 去重（.seen.json 記錄已處理的 platform:review_id）
      └─ 情緒評分（星等硬性決定，LLM 只補敘述）
              │
    ┌─────────┴─────────┐
    │                   │
1–2 星                3–5 星
升級路徑              一般路徑
    │                   │
每則「單獨」推播      併成「一則」彙整
30 分鐘內到手機       下一次通知批次
不等彙整批次          超過 10 則只給統計
```

**為什麼要分兩條路**：把負評丟進彙整批次，等於讓最緊急的那則和九則五星好評排隊。
書中量測到的 48 小時聲譽損害，幾乎都發生在「其實有收到通知，但混在一堆通知裡沒被看見」。
升級路徑的價值不在於偵測得比較快，而在於**它不排隊**。

**為什麼星等決定路由，而不是讓 LLM 決定**：語言模型判錯情緒只是內容不好看；
判錯路由會讓 1 星負評躺在彙整裡過夜——那正是這個模組要解決的問題本身。
LLM 只負責「為什麼」與「怎麼回」，不負責「要不要警報」。

## 為何公開回覆不建議 SUPERVISED_AUTO

本模組的自主權**預設 DRAFT，且不建議調到 `supervised_auto`**。
config 真的改成 `supervised_auto` 時，程式會發琥珀警示提醒你這件事。

| 理由 | 說明 |
| --- | --- |
| **無法撤回** | Email 寄錯還能寄第二封道歉。公開評價回覆在被刪除前的每一秒都可能被截圖，而截圖不會跟著被刪。 |
| **受眾不是抱怨者** | 真正在讀回覆的是還沒下單的潛在客戶。一句語氣失準的自動回覆，傷的是所有後續讀者，不只這一位。 |
| **錯誤成本不對稱** | 自動送出省下的是 60 秒；送錯一則的公關成本是數十小時。書中鐵律「兩週 + 客戶簽核」在此不是保守，是算過的。 |
| **負評本身就是異常** | 需要走升級路徑的，定義上就是最需要人判斷的那幾則。把最難的題目交給全自動，是把安全網掛反了。 |
| **法遵風險** | 補償承諾、退款時程、責任歸屬，一旦寫進公開回覆就具有對外效力。這類句子必須有人簽字。 |

`READ_ONLY` 是合理的另一個選項：只監控與情緒評分、完全不草擬回覆，
適合客戶自己有文案團隊、只想要「不漏看」這一項價值的情境。

## 使用方式

```bash
# 離線跑完整流程（零憑證、零網路）
python main.py --mock

# 推到 Telegram
python main.py --mock --notify telegram

# 只跑流程不發送、也不寫入去重狀態（可重複執行）
python main.py --mock --dry-run

# 串接真實平台（缺憑證會明確報錯，不會靜默退回 mock）
python main.py --live --notify telegram

# 測試
python -m pytest test_main.py -v
```

| 旗標 | 說明 |
| --- | --- |
| `--mock` | 離線模式（預設），讀 `mock/*.json` |
| `--live` | 串真實 API，需要各平台的 token 環境變數 |
| `--dry-run` | 跑完流程但不發送、不寫狀態檔 |
| `--notify` | `console`（預設）/ `telegram` / `gmail` / `line` / `whatsapp` |
| `--config` | 設定檔路徑，預設同目錄 `config.yaml` |
| `--state-file` | 去重狀態檔路徑，預設同目錄 `.seen.json`（測試會指向暫存目錄） |

**live 模式需要的環境變數**（缺哪個就報哪個，不給預設值）：
`GOOGLE_BUSINESS_API_KEY`、`TRUSTPILOT_API_KEY`，
以及所選通知管道的憑證（如 `TELEGRAM_BOT_TOKEN`）。Claude 走本機 `claude` CLI／Max 訂閱 OAuth，不需要 `ANTHROPIC_API_KEY`。

## 設定重點（`config.yaml`）

| 欄位 | 預設 | 說明 |
| --- | --- | --- |
| `monitor.poll_interval_hours` | `6` | 輪詢間隔。排程由外部 cron / 排程器負責，程式本身只跑一輪 |
| `monitor.escalation_threshold_stars` | `2` | 幾星（含）以下走升級路徑 |
| `monitor.escalation_minutes` | `30` | 對外承諾的警報時限，會寫進警報文案 |
| `monitor.fetch_delay_seconds` | `1.0` | live 抓取間隔，程式強制不得低於 1.0 秒 |
| `monitor.seen_state_file` | `.seen.json` | 去重狀態檔名，實際路徑以本檔目錄推算 |
| `monitor.digest_max_items` | `10` | 彙整通知最多列出幾則，超過只給統計 |
| `brand_voice.profile_file` | `mock/brand_voice.json` | 語氣樣本檔；缺檔發琥珀警示（`tone_mismatch`），不中斷 |
| `runtime.autonomy` | `draft` | **不建議改動**，理由見上 |

## 已知限制（預期管理，先講清楚）

| 限制 | 說明 |
| --- | --- |
| Amazon 平台預設關閉 | Amazon 無公開評價 API，需走 SP-API 授權；`config.yaml` 中 `enabled: false`，客戶完成授權後才開 |
| 排程不在本模組內 | 程式只負責「跑一輪」。每 6 小時由 cron / 工作排程器觸發，這樣重試與監控都能交給既有基礎設施 |
| 30 分鐘是「送達」不是「已回覆」 | 代理程式保證草稿在 30 分鐘內到手機；實際送出仍需人工審查（這正是 DRAFT 的用意） |
| 星等解析失敗的評價 | rating 無法解析時記為 0，**走一般路徑**（不強制升級，避免平台改版一次轟炸數十則造成警報疲勞、使用者索性關掉通知），同時發琥珀警示並在彙整通知最前方明確標示「星等無法判讀，請人工確認」——寧可多看一則，不可把負評靜默當成好評 |
| 去重靠 `platform:review_id` | 平台若重發不同 ID 的同一則評價（極少見），會被視為新評價 |
| 狀態檔損毀 | `.seen.json` 讀取失敗時視為首次執行，代價是重複通知一輪，不會漏看 |
