# 模組 #10 — 客戶跟進序列自動化

> **The Money is in the follow-up.**
> 部署 <90 分鐘｜客戶每月回收 12 小時（$960）｜售價 **$350 setup + $90/mo**
> 成效指標：提案轉換率 **18% → 25%+**

---

## 一、B2B 最大的營收漏洞：跟進漏水桶

書中的概念圖只有三個元素，卻解釋了大多數 B2B 公司的營收缺口：

```
        ┌─────────────────┐
        │  已發送的提案    │   ← 你已經付出成本：研究、簡報、報價、來回會議
        └────────┬────────┘
                 │
        ╔════════▼════════╗
        ║  被遺忘的跟進    ║   ← 漏水點。忙碌 → 推遲 → 覺得太遲 → 放棄
        ║   （漏水桶）     ║      客戶沒說不要，只是被別人先跟上了
        ╚════════┬════════╝
                 │  只有 18% 撐到這裡
        ┌────────▼────────┐
        │      成交        │
        └─────────────────┘
```

**關鍵洞察**：漏掉的不是「潛在客戶」，而是**你已經付過錢的潛在客戶**。
提案階段的成本已經沉沒；每一個因為沒跟進而流失的案子，都是全額虧損。

本模組是**補洞的那面盾牌**——不是幫你找更多客戶，而是不讓已經到手的漏掉。

## 三、為什麼「回覆即中止」是最高優先的設計

這是整個模組**唯一不可停用**的規則，優先權高於排程、高於自主權設定、高於任何客製需求。

**理由**：跟進自動化的失敗代價是不對稱的。

| 失敗方向 | 後果 | 可逆性 |
| --- | --- | --- |
| 少發一封跟進 | 損失一次接觸機會 | 可逆（下次補寄即可） |
| 發給已回覆的客戶 | 「我明明回你了」「這是機器人吧」「你們根本沒在看信」 | **不可逆**（信任一旦破壞無法收回） |

一封誤發的跟進信，摧毀的是你前面所有努力建立的專業形象——
而且往往發生在**客戶剛表達興趣**的當下，也就是價值最高的時刻。

### 實作上的兩道閘門

```
排程判定                          實際發送前
────────                          ──────────
sequencer.plan()                  sequencer.assert_can_send()
  → has_replied() 檢查              → has_replied() 再檢查一次
  → 判定 Day N 是否到期
                    ↓ 中間隔著 LLM 生成時間（數十秒到數十分鐘）
                      客戶完全可能在這段空窗回信
```

**只在排程時檢查一次是不夠的**。本模組在每一封信實際送出前都會再查一次
（`FollowUpSequencer.assert_can_send`），正式環境可傳入 `reply_checker` 改成
即時查 CRM / 收件匣，而不是沿用排程當下的快照。

### 判定採「寬鬆」策略

以下**任一**訊號成立即視為已回覆並中止：

1. `has_replied == true`
2. `replied_at` 有值
3. CRM `stage == "replied"`

寧可少發一封，也不要誤發。

### 設定檔改不掉

`config.yaml` 的 `safety.stop_on_reply` 即使被改成 `false`：

- `FollowUpSequencer` 建構子**強制覆寫為 `True`**
- 透過 `Diagnostics.amber()` 發出警示，並寫進執行結果的 `warnings`
- 這是刻意的設計：不可逆的傷害不交給設定檔決定

## 四、序列規格

| 段 | 天數 | 型別 | 目的 | 字數上限 | 提示詞 |
| --- | --- | --- | --- | --- | --- |
| 1 | Day 3 | `gentle_check` | 在「還記得你、但還沒歸檔」的窗口輕推一下 | 80 字 | `prompts/day03_gentle.md` |
| 2 | Day 7 | `case_study` | **帶新東西進來**：同產業案例，給一個今天處理的理由 | 140 字 | `prompts/day07_case_study.md` |
| 3 | Day 14 | `final_check` | 體面收尾，解除壓力（此封回覆率常高於前兩封） | 100 字 | `prompts/day14_final.md` |

- 到期日 = `proposal_sent_at + N 天`，**不用絕對日期**，序列可隨時重新排程而不錯亂
- Day 7 的案例研究依 `industry` 從 `mock/case_studies.json` 挑選，**數字一律取自案例檔，禁止杜撰**
- 時區用標準庫 `zoneinfo`；缺 tzdata 時降級為固定 UTC+8 並發 AMBER，不讓程式掛掉

### 自主權

| 層級 | 行為 |
| --- | --- |
| `draft`（**預設**） | 全部產出草稿，人工審核後送出 |
| `supervised_auto` | 僅自動送給 `approved_senders` 白名單；未命中一律降級為 `draft` |

書中鐵律：**未在 DRAFT 模式運行滿 14 天、且未取得客戶簽核前，不得開啟全自動**。
未滿 14 天就設 `supervised_auto` 會收到 AMBER 警告。

## 八、使用方式

```bash
# 離線跑完整流程（零憑證、零網路）
python main.py --mock

# 推到 Telegram
python main.py --mock --notify telegram

# 跑完流程但完全不發送
python main.py --mock --dry-run

# 串真實 API（走本機 claude CLI／Max 訂閱 OAuth）；缺憑證會明確報錯，不會靜默降級
python main.py --live

# 測試
python -m pytest test_main.py -v
```

### Mock 資料說明（`mock/prospects.json`，6 位潛在客戶）

| ID | 情境 | 預期結果 |
| --- | --- | --- |
| P-1001 | 剛寄提案、尚未跟進 | Day 3 `gentle_check` 草稿 |
| P-1002 | Day 3 已發、未回覆 | Day 7 `case_study` 草稿（挑到 CS-01） |
| P-1003 | Day 7 已發、未回覆 | Day 14 `final_check` 草稿 |
| P-1004 | **已回覆**（CRM 階段仍是 `proposal_sent`） | **中止**（`replied`）— 安全機制主測案例 |
| P-1005 | 已成交 | 中止 |
| P-1006 | 已流失 | 中止（`stage_closed`） |

`--mock` 的基準時間固定在 `config.yaml` 的 `mock.today`，因此每次執行結果完全相同，
狀態檔也不落地，QA 可重複驗證。

## 十、已知限制

- 本 demo 不含 CRM 寫回。正式部署需在 `_process_one` 之後把 `sent` 結果推回 CRM，
  否則下次執行會依賴本機狀態檔判斷已送出項目。
- 回覆偵測在 mock 模式讀的是 `prospects.json` 的快照。正式環境務必傳入
  `reply_checker`，改為即時查詢 CRM 或收件匣。
- 序列僅支援單一語言版本。多語系客戶需為每個語言複製一組 `prompts/`。
