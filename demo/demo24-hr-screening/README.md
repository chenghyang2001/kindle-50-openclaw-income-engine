# demo24 — 無偏見人資招募篩選管線

> 模組 #24｜Level 3 企業級｜部門：人資｜部署 **1 週**｜售價 **$3,200 setup + $1,200/mo**
> 來源：第 07 章 ch07_p07、附錄 G apxG_p10 / apxG_p11

ATS Webhook（Greenhouse / Lever）收到申請的那一刻，管線先把**姓名、性別、年齡、國籍、
照片、畢業年份**整批抹掉，才開始評分；評分只依 `config.yaml` 裡明列的加權條件矩陣，
不看任何人口學訊號。短名單只以匿名識別碼呈現，**要看到是誰，得由招募經理具名核准**，
而且那次核准會被寫進雜湊鏈稽核日誌。

## ⚠️ 這是全案倫理風險最高的模組

其他模組出錯是「信寄錯了」；這個模組出錯是**就業歧視**。因此有四條鐵律，
`main.py` 啟動時逐條檢查，任一條不符即**紅色警報停機**，不降級、不續跑：

| # | 鐵律 | 設定鍵 | 實作落點 |
| --- | --- | --- | --- |
| 1 | 匿名化必須在評分**之前**完成 | `anonymisation_pass: true` | `anonymiser.anonymise_all()` + `verify_batch()` |
| 2 | 只依明列的結構化條件評分 | `structured_criteria_only: true` | `scorer.py`（**完全不含模型呼叫**） |
| 3 | 短名單只呈現匿名識別碼 | `shortlist_presentation: identifiers_only` | `scorer.format_shortlist()` |
| 4 | 揭露身分需招募經理具名確認 | `reveal_requires_manager_approval: true` | `IdentityVault.reveal()` + 稽核事件 |

**這四個開關不是可調參數。** 把 `anonymisation_pass` 改成 `false` 不會讓管線「跳過匿名化」，
會讓管線**拒絕啟動**。可以被設定關掉的防線等於沒有防線。

### 匿名化到底做了什麼

1. **白名單保留**：只留 `keep_fields` 明列的欄位，其餘（含 ATS 沒預告就新增的新欄位）一律丟棄。
2. **自由文字洗白**：把被移除欄位的值從自我介紹、經歷、技能、證照內文中換成 `[REDACTED]`。
   實務上最常見的破口就是自我介紹第一句「Hi, I'm Amara」。
3. **匿名識別碼**：`CAND-<sha256(application_id + salt) 前 8 碼>`，避免由 ID 順序反推投遞先後
   （早投遞者常被無意識地當成「比較積極」）。
4. **上線前最後一掃**：`verify_batch()` 在評分前再確認一次沒有殘留值，有殘留就停機。

刻意**保留**的兩個欄位，理由寫在 `config.yaml` 的註解裡：

- `right_to_work`：法定查核項。只記「可 / 不可」，**不記是哪一國**（國籍已被移除）。
- `years_experience`：能力證據，也是 disqualifier 的依據。

## 評分模型（唯一評分依據）

權重乘數逐字取自 ch07_p07：

| 類別 | 權重 | 意義 |
| --- | --- | --- |
| Must-have | **x3** | 缺少即嚴重扣分的硬性能力 |
| Preferred | **x1** | 加分項，缺少不構成扣分理由 |
| Behavioural | **x2** | 履歷上寫得出來的**具體事件**（不是人格特質） |

分數 = Σ(權重 × 命中比例) ÷ Σ(權重) × 100，命中比例 = min(1, 命中關鍵字數 ÷ `required_hits`)。

三分支處置（apxG_p11）：

| 條件 | 處置 |
| --- | --- |
| 命中 Disqualifier | **立即標記不符合**，不進入排名 |
| 分數 **> 75** | 進入 Shortlist（僅識別碼）。其中排名前 **20%** 觸發非同步影片面試，題目 **4 題** |
| 40 – 75 | 保留待人工複核 |
| 分數 **< 40** | 個人化溫和拒絕信，**延遲 48 小時**發送 |

**分數 100% 由程式算出，模型不參與計分。** 模型只負責把既定結果寫成人話
（面試題、拒絕信），提示詞裡明文禁止它調整分數或推測任何受保護特徵——
見 `prompts/screening_rubric.md` 的「你的角色邊界」。

為什麼評分要離開模型：就業歧視訴訟的攻防點是「你憑什麼刷掉我」。
分數若來自模型的自由判斷，就無法在法庭上重現當時的計算。

## 稽核軌跡

`state/audit-log.jsonl`（可用 `--audit-file` 覆寫），每行一筆 JSON，欄位為
`seq / ts / module / event / actor / detail / prev_hash / entry_hash`。

`entry_hash = sha256(prev_hash + 本筆內容)`。有人事後手動刪掉某一行
（例如一次未經核准的 `reveal`），`AuditLog.verify_chain()` 立刻指出斷點。
這擋不住整份檔案被抽換，但能讓「偷改一行」變成看得見的事件——
招募稽核的真實威脅模型本來就是內部人的小幅竄改。

記錄的事件：`preflight_passed` / `preflight_missing` / `bias_switch_breach` /
`anonymisation_completed` / `rejection_scheduled` / `rejection_sent` /
`rejection_drafted` / `identity_revealed` / `identity_reveal_denied` / `screening_completed`。

> 稽核是本模組自行實作（`audit.py`），**沒有動 `_shared/`**：其他九個模組沒有法遵留痕需求，
> 把它塞進共用層等於讓所有模組背上用不到的相依，也會單方面撐大凍結契約。

## 快速上手

```bash
# 零憑證、零網路，跑完整條流程（讀 mock/applications.json 的 7 份履歷）
python main.py --mock

# 看完整結果結構（含每位候選人的命中證據）
python main.py --mock --json

# 跑完流程但不發送；同時完成對外送出前必要的內部通訊測試
python main.py --dry-run

# 狀態檔與稽核日誌放到指定位置（正式部署請放在有備份的路徑）
python main.py --mock --state-file ~/hr/state.json --audit-file ~/hr/audit.jsonl

# 推進時間，驗證 48 小時延遲的拒絕信會在到期後送出
python main.py --mock --now 2026-08-26T10:00:00+00:00

# 揭露某位短名單成員的真實身分（缺 --approved-by 會被拒絕並留下稽核紀錄）
python main.py --mock --reveal CAND-xxxxxxxx --approved-by "Nadia Farrell" --reveal-reason "安排一面"

# 真實模式（需 ANTHROPIC_API_KEY / GREENHOUSE_API_KEY / GREENHOUSE_WEBHOOK_SECRET）
python main.py --live --applications ./ats-export.json

# 測試
pytest test_main.py -v
```

| 旗標 | 用途 |
| --- | --- |

## 已知限制與法遵責任

> **本節為本專案的實作補充，不是原簡報內容。** 原簡報只講「BIAS_MITIGATION 開關」，
> 沒有討論殘餘偏見與法遵邊界。這一節是交付前必須跟客戶講清楚的部分。

### 1. 匿名化無法消除所有間接偏見訊號

抹掉姓名、性別、年齡、國籍、照片之後，履歷裡**仍然**帶著大量可推斷受保護特徵的代理訊號：

| 殘餘訊號 | 可能洩漏什麼 | 本模組的處理 |
| --- | --- | --- |
| 校名 | 社經背景、國籍、年齡層 | 已列入 `remove_fields` 一併移除 |
| 畢業年份 | 年齡 | 已移除，並從內文洗掉 |
| 公司名、專案名 | 產業圈子、地域、規模偏好 | **未處理**（移除會讓經歷失去意義） |
| 用語習慣、拼寫風格 | 母語、教育背景、世代 | **無法處理** |
| 年資長度 | 年齡的強代理變數 | **刻意保留**（是職缺的合法要求，但請注意它同時是年齡代理） |
| 空窗期 | 育嬰、照護、健康狀況 | **未偵測、未評分**（本模組不看空窗，這是刻意的） |

換句話說：**這套系統降低偏見，但不消除偏見。** 任何宣稱「完全客觀」的說法都是不實陳述，
提案時不要那樣講。

### 2. 本工具不可作為唯一錄用依據

- 本管線輸出的是**短名單**，不是錄用決定。
- 最終決定必須由**人**做出，而且該決定者必須能**獨立說明理由**——
  「系統給他 82 分」不是理由，「他在 X 條件上有 Y 證據」才是。
- 關鍵字命中不等於能力：履歷寫了 `Kubernetes` 不代表他會，沒寫也不代表不會。
  這正是為什麼 40–75 分區間是「保留待人工複核」而不是自動淘汰。
- Disqualifier 規則（工作權、年資門檻）會直接淘汰，**請務必逐條確認每一條都有合法依據**，
  並且是該職缺真正的必要條件，而不是方便篩人的門檻。

### 3. 各國就業歧視法規不同，部署前須經法遵審閱

- 英國 Equality Act 2010、歐盟 AI Act（招募屬**高風險 AI 系統**）、
  美國 EEOC / Title VII 與紐約市 Local Law 144（自動化招募工具的**年度偏差稽核**義務）、
  各地個資法（GDPR 第 22 條「自動化決策」與資料保留期限）——要求彼此不同，且持續變動。
- **部署前務必經客戶的法遵或勞動法顧問審閱**，特別是：
  1. 條件矩陣的每一條是否構成間接歧視
  2. 是否需要向求職者揭露「本次篩選使用了自動化工具」
  3. 履歷與稽核日誌的保留期限與刪除義務
  4. 是否需要提供人工複核的申訴管道
- 本專案**不提供法律意見**。上面的清單是提醒你要問誰，不是答案。

### 4. 技術面的已知限制

- **關鍵字比對是字面比對**：`k8s` 不會命中 `kubernetes`。條件矩陣要靠人工維護同義詞，
  維護不足會系統性地淘汰用詞習慣不同的人（這本身就是一種偏見）。
- **匿名化採詞邊界比對**：住址 token `View` 不會誤傷 `code review`，但也代表
  複合詞裡的姓名（如 `amaraokoye123`）可能洗不掉。`verify_batch()` 會抓到並停機。
- **IdentityVault 只存在記憶體中**：跨執行不保留，因此 `--reveal` 必須與篩選在**同一次執行**內完成。
  這是刻意的取捨——把姓名對照表落地到磁碟，等於製造一個新的外洩面。
- **狀態檔存有 `identifier → ats_reference` 對照**：這是回寫 ATS 的必要之惡。
  狀態檔的存取權限應等同 ATS 本身，不要放在共享目錄。
