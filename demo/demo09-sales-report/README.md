# demo09 — 每日銷售與進度報表

> 模組 #9 ｜ 階段：業務增長 ｜ 部署 < 60 分鐘 ｜ 回收 11 hrs/mo

Agent 每天早上自動連接 **CRM / Shopify / Stripe**，計算與目標的差距、標記異常，
並在 **07:00 準時**把排版好的報表送到團隊信箱。

## 為什麼要有「部分失敗」設計（本模組最重要的決策）

一般的做法是：任一資料源取不到就中止，寄一封錯誤信給工程師。
**這個模組刻意不那樣做。**

理由有三個：

1. **整份失敗會讓 Agent 重現它要消滅的舊狀態。**
   客戶付錢買的價值是「早會不用再現場組資料」。Stripe 掛掉那天如果整份報表不發，
   團隊就退回到憑印象開會——跟導入前一模一樣，而且還多了一份被辜負的期待。
   三個資料源當中壞掉一個，剩下 2/3 的數字**仍然有決策價值**。

2. **殘缺數據的真正風險不是「不完整」，而是「看起來完整」。**
   所以缺資料時的處理是**加標記**，不是**補數字**：
   - 報表最上方強制加橫幅：`⚠️ 部分資料：Stripe 無回應`
   - 橫幅下一行明寫「請勿據此下修目標或究責」
   - 失敗的資料源仍然列在明細裡（標 ⚠️ 與失敗原因），不會從報表上消失
   - 提示詞（`prompts/report.md`）明令 AI **不得推估、補值或杜撰**缺失資料源的數字
   - 缺數的資料源不會被當成 0 加總——0 元和「不知道」是兩件事

3. **維運端仍然必須被通知。** 「照常發出」不等於「假裝沒事」。
   每個失敗資料源都會走 `Diagnostics.amber(symptom, fix)` 進入 RAG 診斷矩陣的琥珀燈：
   流程繼續、但留下明確的症狀與修法。只有系統性失效才走紅燈退出
   （例如 `--live` 缺憑證——這種情況寧可不跑，也不能靜默降級成 mock）。

一句話：**降級，但絕不假裝。**

## 異常標記規則

| 規則 | 閾值 | 為什麼 |
| --- | --- | --- |
| 達成率過低 | < 80% | 落後到需要當天處理，而不是月底才發現 |
| 達成率過高 | > 150% | 超標同樣可疑：多半是重複計算、測試訂單或一筆特大單，需要人確認 |
| 偏離 7 日均值 | 絕對值 > 30% | 抓「跟平常不一樣」，補足「跟目標比」看不出的異常 |

閾值全部寫在 `config.yaml` 的 `thresholds`，不寫死在程式碼。

**異常規則只套用在「當日」達成率，不套月進度**：月中任何一天的月累計天然低於 80%
（例如 24 號才跑到 66%），套下去每天都會噴假警報，一週內團隊就會把警示當成背景雜訊。
月進度只做資訊呈現。

## 財務模型（Financial Model）

| 項目 | 數值 |
| --- | --- |
| 部署時間 | < 60 分鐘 |
| 客戶每月回收 | 11 hrs/mo |
| 回收價值 | **$825 /mo**（以 $75/hr 計） |
| 建置費（Setup） | **$300** |
| 月費 | **$80 /mo** |
| 客戶第一個月成本 | $380 |
| 客戶第一個月淨賺 | **+$445** |
| 客戶年度淨值 | $9,900 − $1,260 = **+$8,640** |
| 投資回收期 | **不到 2 週** |

客戶端的算式很好講：每月 $80，換回 11 小時、$825 的價值。
**10 倍回報，第一個月就轉正。**

供給端（你）：部署一次 < 60 分鐘，之後每月 $80 是近乎純被動收入。
接 10 個客戶 = $800/mo 經常性收入，維護成本主要是資料源憑證過期時的處理。

> 本模組也是「快速啟動方案」打包（#1 + #2 + #5 + #9，$995 setup + $200/mo）的成員之一。

## 執行方式

```bash
# 零憑證、零網路，讀 mock/*.json 跑完整流程
python main.py --mock

# 推到 Telegram
python main.py --mock --notify telegram

# 跑完流程但不發送
python main.py --mock --dry-run

# 串真實 API（缺憑證會列出缺哪些變數並退出，不會靜默退回 mock）
python main.py --live

# 測試
python -m pytest test_main.py -v
```

### 三個資料源為什麼可以直接相加

因為它們代表**互不重疊**的營收管道：

| 資料源 | 代表 | 淨額口徑 |
| --- | --- | --- |
| CRM | 業務直簽成交（closed won） | 只計已成交，銷售管道總值不計入營收 |
| Shopify | 電商訂單 | 已付款訂單 − 當日退款 |
| Stripe | 訂閱與一次性收款 | 成功收款 − 金流手續費 |

三者都是淨額，因此相加不會重複計算。銷售管道（pipeline）總值只做資訊呈現——
把「還沒收到的錢」算進當日營收，是這類報表最常見的信任殺手。

## 技術要點

- **金額全程 `Decimal`**：JSON 與 YAML 的金額一律以字串儲存（`"4200.00"`），
  避免 float 二進位誤差在月累計時被放大成 `61449.999999999996`。
  收斂用 `ROUND_HALF_UP`（財務慣例），不用 Decimal 預設的銀行家捨入。
- **自主權階梯**：報表會對外發送，依第 04 章鐵律預設 `draft`。
  非 console 通道要真的送出，需 `supervised_auto` + 非空白名單 + 連續穩定 14 天。
  console 通道視為本機列印，不受閘門管制。
- **除以零**：每日目標為 0 時，達成率回 `None` 而不是 0，並標記異常提醒檢查目標設定。
- **設定錯誤不靜默**：`deliver_at` 格式錯誤直接拋錯，不悄悄套用預設值——
  否則「為什麼報表沒在我設定的時間送出」會變成無解懸案。

## 已知限制

- 目前三個資料源都是 mock 讀檔；`--live` 的真實 API 串接需補上各自的 client。
- 7 日均值取自 `targets.json` 的快照，未做真實的歷史資料庫查詢。
- 時區僅用於報表顯示，實際排程由外部 cron / 排程器負責（建議設 06:40 觸發，
  留 20 分鐘緩衝，確保 07:00 前送達）。
